## 11.1 交付物的三项通用要求

在列清单之前，先定三条对**所有**交付物都适用的标准：

| # | 要求 | 判定 |
|---|---|---|
| **T-1** | **可验证**：每个交付物必须有「怎么知道它做对了」的方法 | 无判定方法的交付物 = 不算交付 |
| **T-2** | **可追溯**：每个交付物必须能指回某个 `ID`（`L-` / `V-` / `O-` / `M-` / `A-` / `G-`） | 否则它是「谁也没要求过的东西」 |
| **T-3** | **无孤儿**：不存在「代码里有但文档没写」或「文档写了但代码没有」的条目 | 双向对账 |

T-3 是最容易被忽略的一条。本计划已经出现过一次：`WedoGlassTokens.kt` 202 行活着、`Modifier.wedoGlass` 死了、单测还在测它——**这就是孤儿**。

## 11.11 交付物的验收方式（谁来验、怎么验、不过怎么办）

七类交付物的验法不同。混用会导致「代码写完了就当交付完成了」。

| 类 | 谁验 | 怎么验 | 不过的处置 |
|---|---|---|---|
| 代码模块 | 任何人（编译 + 测试） | `Q-01`/`Q-02` + 16 个文件的调用方检查 | 编译不过 → 不进该阶段；零调用方 → 删 |
| 设计规范 | 人工评审（对照附录 F 勾选） | 72 条逐条勾 | 有未勾项 → 不进 P6 |
| 配置文件 | **必须在 release 变体验** | minify 构建 + 真机安装 + 打开 | 崩 → 回退 keep 规则，重新定位 |
| 测试用例 | 任何人 | `testDebugUnitTest` 数 ≥ 870 且 failures = 0 | 数不够 → 补；红 → 修 |
| 测试报告 | 人工核对数据 | 22 组对比度表 + framestats 摘要 | 数据缺 → 补测 |
| 视觉对照材料 | **只能用户验** | 按截图指引拍，我对照判定 | 用户未回传 → 状态是「未验证」不是「通过」 |
| 维护文档 | 人工抽查 | 抽 3 个常量看 KDoc 四要素、抽 1 条 PATCH 看格式 | 缺要素 → 补写 |

### 11.11.1 一条容易被忽略的验收

**「16 个新文件各有 ≥1 处生产调用方」**（`A-24` / `G-072`）必须单独验。

理由：本项目的 `WedoGlassTokens.kt` 就是「零生产调用方但一直活着」的先例——202 行，唯一消费方是单测。**它不是坏代码，是没有主人的代码。**

验法：

```
对 16 个文件逐个：
  grep -rn "GlassCapture\|GlassSnapshot\|..." ui/screen ui/component MainActivity.kt
  命中数 == 0 → 孤儿，必须删或接入
```

### 11.11.2 验收的「三不」原则

| # | 不 | 理由 |
|---|---|---|
| 1 | **不用「代码写完了」代替「验过了」** | 这两件事在本项目历史上多次分离（2026-09-27 的 27 个测试全绿） |
| 2 | **不用「测试全绿」代替「视觉通过」** | 契约测试只验接线，不验观感 |
| 3 | **不用「应该没问题」代替「未验证」** | 未验证是一个合法状态，伪装成通过才是缺陷 |
