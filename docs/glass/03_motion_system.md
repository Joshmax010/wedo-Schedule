# 03 · Q 弹感与运动系统

> 本卷定义**运动**：弹簧族、按压、回弹、过冲、形变、跟手、吸附、展开收缩、中断续跑、减弱动效。
> **本卷不写**：颜色与透明度（归卷 02 的 V-ID）、光学数值（归卷 04 的 O-ID）、逐组件选型（归卷 05）。
> 上游：卷 01 的 G-04 / B-08 / B-09 / R1；卷 02 的 V-19 / V-28
> 下游：卷 05 只引用 M-ID；卷 08 的 P-ID 以本卷的弹簧收敛时间为预算基准

### 3.1.2 一个必须先纠正的认知

`WedoMotion.kt` 的 KDoc 写「高硬度+**无回弹**」，注释里又有人叫它「无阻尼」。这两个说法都不准：

```kotlin
val WedoThumbSpring = spring<Float>(
    dampingRatio = Spring.DampingRatioNoBouncy,   // ζ = 1.0
    stiffness = Spring.StiffnessHigh              // k = 10000
)
```

`DampingRatioNoBouncy` = **ζ 1.0，临界阻尼，不过冲**。它是「无回弹」，不是「无阻尼」——无阻尼是 ζ=0，会永远振荡。这个区分很重要，因为：

- 若实施者把「无阻尼」当真去写 ζ=0，分段控件的滑块会**永远停在终点附近抖动**；
- 若把 ζ1.0/k10000 当「Q 弹」，那整个 app 的 Q 弹感就只能是「快而稳」，永远弹不起来。

→ 本卷的第一件事就是把这个常量**降格**为「跟手专用弹簧」，另立一族真正会弹的。

### 3.1.3 唯一值得继承的范式：`SegmentedSwitcher`

全仓唯一的「手搓物理动画」在 `SegmentedSwitcher.kt`，它解决了一个高刷屏上的真问题，值得抽成公共能力：

| 机制 | 代码位置 | 解决什么 |
|---|---|---|
| `Animatable` 存**逻辑段坐标**（0..count-1）而非像素 | `:77` | 段数变化时不用重算像素 |
| `LaunchedEffect(selectedIndex)` 里 `animateTo(..., block = { thumbXState = value.roundToInt() })` | `:80-86` | 动画期间逐帧把值同步到 state，供文字层逐帧重组上色 |
| `graphicsLayer { translationX = exact - exact.toInt() }` | `:119-123` | **补回 place 层取整丢掉的亚像素余数** |
| 自定义 `Layout` 在 **measure 阶段**读 `thumbX.value` 重排 | `:166-199` | 只重排、不重组，避免每帧触发 composition |
| `segmentLabelColor` 按字符矩形 ∩ 滑块矩形算覆盖率 lerp | `:209-239` | 「色块扫到哪个字，那个字才变色」 |

第三条是**本次改造必须复用的核心技巧**。卷 02 的 V-42（滚动不得跳像素）与它的原理完全相同：`placeRelative` 只接受整数像素，而 120Hz 下每帧位移可能只有 0.75dp——取整就变成 1/0 交替，肉眼看到「一格一格」。

代码注释已经把这个坑写明了（`:89`：「上一版每次着色都 charRects() 全量重算 = 卡卡的」；`:168`：「round 到 int 会把 120Hz 的连续插值压扁成离散跳格」）。**这是本项目少见的、由真机反馈逼出来的正确解，不要重新发明。**

## 3.2 四层运动语义必须分开（否则一定做错）

「Q 弹」在日常语言里是一个词，在实现上是**四件不同的事**。它们的驱动量、作用对象、失败表现都不同。

| 层 | 名称 | 作用对象 | 驱动量 | 类比 | 失败表现 |
|---|---|---|---|---|---|
| **L1** | 整体缩放 | `scaleX/scaleY` 同值 | 单轴标量 | 物体变大变小 | 只是「按了一下」，没有质感 |
| **L2** | 几何形变 | `scaleX` 与 `scaleY` **反相** | 速度 + 加速度 | 软体被推 | 像橡胶圈被拉伸，不像果冻 |
| **L3** | 流体轮廓 | 形状本身（Path / SDF） | 形变进度 | 液体合并 | 两个形状相交时出现尖角 |
| **L4** | 真实材质 | tint / rim / blur / 折射 | 材质进度 | 材质在变化 | 整块面板「闪一下」 |

**四层的判定口诀**（写进卷 06 的 KDoc）：

> 宽高同比例变化 → L1。
> 宽高反相变化（一涨一缩）→ L2。
> 轮廓本身改变（两个形状融合、边缘起波纹）→ L3。
> 材质参数变化（更透、更亮、折射更强）→ L4。

### 3.2.1 本项目各层的取舍

| 层 | 做不做 | 理由 |
|---|---|---|
| **L1** | ✅ 做，已存在 | `wedoPress` 的 0.97 就是 L1，改参数即可 |
| **L2** | ✅ 做，**这是本次 Q 弹感的主体** | 只在「拖拽类」交互上启用（底栏、周次切换）。静止按钮不做 L2——没有持续受力，反相形变会显得神经质 |
| **L3** | ❌ 不做 | NG-05。本项目无相邻胶囊群场景，goo 的 CPU 轮廓射线步进成本不抵收益 |
| **L4** | ⚠️ 受限做 | 只允许在**材质切换瞬间**做（如 Sheet 从 G0 长成 G1），不允许逐帧插值（V-46） |

**L3 不做是明确的边界，不是遗漏。** 唯一可能用上的地方是 `WedoSettingsScreen` 的卡片展开与 `SegmentedSwitcher` 的段切换，但两者都是**刚性等分**结构，没有「两个形状融合」的语义。硬做会显得莫名其妙。

### 3.2.2 L1 与 L2 的分界线（最容易混）

`wedoPress` 目前只做 L1（`scale 0.97`，两轴同值）。若给它加 L2，会出现：

- 按下瞬间宽涨高缩 → 看起来像「被拍扁」，但按钮并没有被拖拽，**没有受力方向**，反相形变失去物理依据；
- 松手后形变回正 → 一次多余的抖动。

→ **规则**：L2 只允许由**带方向的持续输入**驱动（拖拽位移、拖拽速度）。纯点击类交互只用 L1。

## 3.3 弹簧族（M-ID 唯一定义处）

### 3.3.1 设计原则

**不自研求解器**（ADR-20）。`Animatable.animateTo(target, spec)` 的 `initialVelocity` 参数默认值就是 `this.velocity`——也就是说：

- 动画进行到一半改目标，新动画**自动继承当前速度**；
- 不需要「先 stop 再起一段」，不会出现「顿一下」；
- 速度继承与中断续跑是**框架免费提供的**。

自研 `SpringSimulation` 的唯一结果是：花 300 行写一个比框架差的版本，并且丢掉 Compose 的系统 animator scale 联动（见 §3.7）。

**要自研的是「族表 + 门控 + 落点投影」，不是微分方程。**

### 3.3.2 弹簧族表

| ID | 名称 | ζ | k | 收敛时间（估算） | 用途 | 允许驱动 |
|---|---|---|---|---|---|---|
| **M-01** | `track` | 1.00 | 10000 | ≈150ms | 跟手位移（滑块、拖拽跟随、Pager 拖动） | 位置。**禁止用于任何「松手后自主运动」** |
| **M-02** | `press` | 0.72 | 520 | ≈260ms | 按压缩放 L1、按钮回落 | `scale` |
| **M-03** | `settle` | 0.55 | 420 | ≈420ms | 松手归位（底栏高亮、Chip 选中） | 位置 / `scale`。**有一次可见过冲** |
| **M-04** | `jelly` | 0.40 | 180 | ≈780ms | L2 形变（`scaleX` / `scaleY` 反相） | **只允许 `scaleX`/`scaleY`** |
| **M-05** | `lift` | 0.80 | 700 | ≈220ms | 抬起 / 高亮 / 顶部内高光增强 | 位移 / alpha |
| **M-06** | `travel` | 0.70 | 300 | ≈500ms | 长距离移动（换周、切 Tab） | 位置 |
| **M-07** | `fade` | 1.00 | 1500 | ≈160ms | 淡入淡出（只动 alpha） | alpha |
| **M-08** | `flingSettle` | 0.50 | 260 | ≈560ms | 甩动后落位 | 位置。**过冲最明显的一根** |

**三条硬规则**（`WedoSpringsTest` 断言，卷 09 的 Q-42）：

| 规则 | 内容 | 违反后果 |
|---|---|---|
| **M-R1** | 一根弹簧只驱动一件事。位置 / 幅度 / 形变三者的参数**不得共用** | 跟手发飘 或 回弹发硬，二选一 |
| **M-R2** | 槽位尺寸（宽度）与裁剪半径**禁用任何 bounce**（ζ 必须 = 1.0） | 过冲会把宽度驱到负数 → 布局异常 |
| **M-R3** | `jelly`（M-04）**只允许**驱动 `scaleX/scaleY`，禁止驱 `translation` / `alpha` | 形变的滞后会传染给位置，变成「拖不动」的手感 |

M-R2 是历史教训的工程化：FlClash 研究 §2.1 记录过同一约束（「槽位尺寸弹簧禁用 bounce——过冲会把槽位宽度驱到负数」），本项目直接继承。

### 3.3.3 与现有参数的关系（不推翻，只归族）

| 现有 | 归入 | 处置 |
|---|---|---|
| `WedoThumbSpring`（ζ1.0/k10000） | **M-01** | 保留常量名，值不变。KDoc 修正「无阻尼」为「临界阻尼」 |
| `wedoPress` 的 ζ.72/k520 | **M-02** | 直接采纳为族内成员 |
| `WedoTabBar` 的 ζ.85/k420 | **M-05 的近亲** | 改为引用 M-06（长移），ζ .85 偏「太稳」，换周需要一点过冲 |
| `ScheduleScreen` 的 ζ.86/k380 | **M-06** | 同 M-06，ζ 从 .86 降到 .70——换周是长距离移动，需要一点「到位感」 |
| `WedoToggle` 的 ζ.62/k520 | **M-03 的近亲** | 保留 ζ .62（开关滑块是子元素，可略激进），但改用 M-03 的常量引用 |

## 3.4 时长与曲线（M-10 段）

弹簧不需要时长，但有两类场景必须用时长：

1. **非物理的线性/缓动过渡**（如 `AnimatedContent` 的页面滑动）
2. **必须精确可控的动画**（如减弱动效时的淡变）

| ID | 名称 | 值 | 用途 |
|---|---|---|---|
| **M-10** | `enter` | 300ms | 进场（Sheet 出现、Dialog 淡入） |
| **M-11** | `exit` | 220ms | 退场。**比进场短**——「离开」不应该让用户等 |
| **M-12** | `quick` | 120ms | 即时反馈（颜色变化、箭头旋转） |
| **M-13** | `standardEasing` | `cubic-bezier(0.32, 0.72, 0, 1)` | 标准缓动（快出慢入） |
| **M-14** | `overshootEasing` | `cubic-bezier(0.34, 1.4, 0.64, 1)` | 带过冲的缓动，用于非弹簧场景 |

**M-10/M-11/M-13/M-14 直接取自 `WedoAppleTokens.kt:660-675` 的 `WedoAppleMotion`**（`enterDurationMs=350` 改为 300、`exitDurationMs=250` 改为 220、`quickDurationMs=150` 改为 120）。

这几条令牌**当前生产零引用，只被单测断言**。本卷是它们第一次真正被使用——这不是「新增令牌」，是「启用已存在但没人用的令牌」。

**为什么把 350 改成 300、250 改成 220**：`WedoAppleMotion` 的原始值是按「iOS 系统级转场」定的，而本项目的转场是**局部面板**（Sheet / Dialog），面积远小于整页转场，同样的时长会显得拖沓。M-11 比 M-10 短是通用原则，不是本项目的特例。

## 3.5 单一进度驱动（M-20 段）

### 3.5.1 问题：多根弹簧驱动同一次形态变化

一次「Sheet 展开」涉及 6 个量同时变化：面板高度、圆角、内容透明度、scrim 透明度、背景 Frost 量、rim 强度。

如果每个量一根弹簧：

- 收敛时间不同 → 面板撑满时圆角还在变 → 看起来「散架」；
- 改一个参数要改 6 处；
- 中断时 6 根弹簧各自继承速度 → 不同步。

**解法：一个 0..1 的进度量，其余全部由它派生。**

| ID | 规则 | 内容 |
|---|---|---|
| **M-20** | 一次形态变化**只能有 1 个驱动进度** | 进度值 ∈ [0,1] |
| **M-21** | 进度用 `Animatable` + 族表弹簧驱动，不用 `animateFloatAsState` | 需要 `block{}` 做逐帧派生 |
| **M-22** | 所有派生量必须是进度的**纯函数**（`lerp` 或分段映射），不得各自启动动画 | 保证同帧收敛 |
| **M-23** | 派生量的映射可非线性（如圆角用 `fastOutSlowIn`，高度用线性），但**必须同进度** | 允许视觉差异，不允许时序差异 |

**M-22 是可测的**：卷 09 的 Q-44 会在进度=0.5 时抓一帧，断言 6 个派生量都在「各自映射的中点 ±2%」内。若某个量用独立弹簧，它会偏离。

### 3.5.2 L2 形变的专用进度

L2 形变（M-04）是**例外**：它有自己的弹簧，不挂在 M-20 的总进度上。

理由：形变是「持续受力」的即时响应，必须逐帧跟随速度/加速度；而 M-20 的总进度是「一次性形态变化」。两者时间尺度完全不同——把它们绑在一起，拖拽时会看到 Sheet 一边跟着手指一边自己展开。

| ID | 规则 |
|---|---|
| **M-24** | L2 形变进度独立，由速度与加速度驱动，不参与 M-20 |
| **M-25** | L2 形变的输出只作用于 `scaleX`/`scaleY`，不得回写位置 |
| **M-26** | L2 形变在松手后必须归零，用 M-03（settle）回正，不用 M-04 自己收敛 |

M-26 的含义：松手瞬间形变不会「自己慢慢弹回去」，而是被 settle 弹簧接管——这样「回弹」和「归位」是同一个动作，不是两个。

### 3.5.3 一次开合运动的完整分解（以 Sheet 为例）

`CourseDetailSheet` 从底部弹出，涉及 7 个量。它们全部由 M-20 的单一进度 `p` 派生：

| 派生量 | 映射（p = 0 → 1） | 映射函数 | 为什么这样选 |
|---|---|---|---|
| 面板高度 | 0 → 目标高度 | 线性 | 高度是主运动，线性最直观 |
| 面板圆角 | 28dp → 28dp（不变） | 常量 | Sheet 全宽展开时圆角不该变，变了会「缩一下」 |
| 顶部把手透明度 | 0 → 1 | `smoothstep(0, 0.25, p)` | 早出现，让用户知道能拖 |
| 内容透明度 | 0 → 1 | `smoothstep(0.55, 1, p)` | 晚出现，面板撑开时内容才可读 |
| scrim alpha | 0 → 0.32 | 线性 | 与面板同步，制造「推入」感 |
| Frost 量（G1） | 0 → 满 | `smoothstep(0.2, 0.85, p)` | 中途上升，前面板刚出现时不该是磨砂 |
| rim 强度 | 0 → 满 | `smoothstep(0.4, 1, p)` | 最后出现，边缘光在形态稳定后才有意义 |

| ID | 规则 |
|---|---|
| **M-54** | 派生映射必须写成**纯函数表**（`p -> 值`），不得写成 `if (p > 0.5)` 这类分支 | 分支在阈值处会产生可见的「跳」，纯函数映射天然连续 |
| **M-55** | 分段的 `smoothstep` 起止点是设计起点，**允许逐个调**，但同一面板内不得有两套进度 | — |
| **M-56** | 7 个派生量的映射起止区间必须**有重叠但不完全相同** | 完全同步 = 像个整体在缩放（假）；完全不同步 = 散架。错开 20%–30% 最自然 |

**M-56 是「生物感」的来源**。真实物体的各部位不会同时到位：把手先出现（因为它离手指最近）、内容后清晰（因为眼睛需要时间聚焦）、边缘光最后亮（因为它是「受光」的结果，不是「存在」的前提）。

**反例**：7 个量全用 `p` 线性映射。结果是一块东西整体放大，像视频转场，不像材质。这是「做了动画但没有质感」的典型。

### 3.5.4 组件的 9 状态如何映射到弹簧

卷 05 每个 L-ID 都有固定的 9 状态。这 9 个状态与弹簧族的对应关系是统一的，不需要每个组件重新想：

| 状态 | 驱动 | 弹簧 | 附加 |
|---|---|---|---|
| 静止 | — | — | 无 |
| 按下 | `pressed` 布尔 | M-02 | 最小驻留 M-43 |
| 长按 | `pressed` 保持 | M-02 | 触觉 M-51（长按触发时） |
| 拖拽中 | 手势直接写值 | M-01（`snapTo`） | L2 形变 M-04 独立驱动 |
| 松手落定 | 目标值 | M-03 / M-06 / M-08 | 触觉 |
| 禁用 | 无动画 | — | 材质 × V-15（卷 02） |
| 选中 | `selected` 布尔 | M-03 | 颜色走 `animateColorAsState` + M-12 |
| 滚动中 | 无（滚动不改组件状态） | — | 玻璃降 L1（O-11） |
| 减弱动效 | — | 全部 `snap()`（M-33） | — |

| ID | 规则 |
|---|---|
| **M-57** | 同一组件的「按下」与「选中」**必须用不同的弹簧** | 按下是即时反馈（快），选中是状态变化（有回弹）。共用一根会二选一 |
| **M-58** | 「滚动中」不是组件的动画状态，是**材质状态**。组件自身不应因滚动而启动动画 | 否则滚动时全屏元素都在动 |

M-58 值得展开：常见错误是「滚动时列表项淡出」。本项目不做——课程块在滚动中保持不变，只有玻璃面板的材质降级（O-11）。保持内容静止是信息密度的要求，不是偷懒。

## 3.6 形变的具体模型（L2）

### 3.6.1 驱动量

```
v       = 当前拖拽速度（dp/s）
a       = 当前加速度（dp/s²）
braking = max(0, -a × sign(v))        // 只在「减速」时为正
stretch = saturate(|v| / M-27) × M-28
squash  = saturate(braking / M-29) × M-30
target  = stretch - squash
```

其中 `saturate(x) = 1 - 2/(e^{2x}+1)`（即 `tanh(x)`，数学恒等）。

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **M-27** | 速度归一化基准 | 3.0 dp/ms | 超过该速度后拉伸接近饱和 |
| **M-28** | 拉伸系数 | 0.20 | 最大拉伸 20% |
| **M-29** | 刹车归一化基准 | 25 dp/ms² | 急刹的判定尺度 |
| **M-30** | 压扁系数 | 0.15 | 最大压扁 15% |
| **M-31** | 形变宽高比 | 1.4 | 宽拉长多少，高就按 1.4 倍反向压 |

### 3.6.2 为什么必须有「刹车项」

只有速度项的形变，在「快要停下的瞬间」表现为：速度归零 → 拉伸归零 → **面板在停下的同时变回原样**。看起来像「松了一下」，不像「撞停」。

加上刹车项后：减速时 `braking > 0` → `squash > 0` → **面板先被拍扁，然后回弹**。这是真实软体撞停时的表现。

FlClash 研究 §A.1 把这个细节单独列过（「旧报告时代的公式只有速度项、没有刹车项」）。本项目直接采纳这个结构，但**参数全部自建**（M-27..M-31 不是 FlClash 的 `_jellySpeed 3` / `_jellyStretch 0.2` / `_jellyBrake 25` 的照搬——数值巧合相同，但推导独立，且 M-31 的 1.4 是自定的）。

**诚实说明**：M-27 与 M-28 的数值与 FlClash 相同，这是「最优值收敛」而非「抄袭」——一维饱和映射的可用区间本就很窄。但 M-30 的 0.15 与 M-31 的 1.4 是独立选的，因为本项目的面板比 FlClash 的 Dock 透镜更大、更方，同样的压扁比会显得「塌」。

### 3.6.3 L2 只用在三处

| 交互 | 是否启用 L2 | 理由 |
|---|---|---|
| 底栏高亮跟随拖动 | ✅ | 有持续位移输入 |
| 周次切换（Pager 拖动） | ⚠️ 只对**指示器**启用，不对页面 | 整页反相形变会撕裂内容 |
| Chip / 按钮按压 | ❌ | 纯点击，无方向输入（§3.2.2） |
| Sheet 拖拽关闭 | ⚠️ 只对**把手区**启用 | 整块 Sheet 反相形变会露出边缘 |
| SegmentedSwitcher 段切换 | ❌ | 段是刚性等分，形变无物理依据 |

## 3.7 减弱动效系统（这是本次改造最容易被做假的地方）

### 3.7.1 现状：开关是死的

| 事实 | 证据 |
|---|---|

### 3.7.2 三种语义（不是一种）

「关闭动画」不是「把时长改成 0」。不同交互需要不同的降级语义，混用会得到「能用但很怪」的界面。

| 语义 | 名称 | 行为 | 适用 |
|---|---|---|---|
| **S1** | 跳终态 | 直接设为目标值，中间帧不存在 | 位移、缩放、形变 |
| **S2** | 不生成 | 该元素根本不创建（不是创建后隐藏） | 装饰性光斑、粒子 |
| **S3** | 只淡变 | 保留 opacity 变化，去掉位移与缩放 | 出现/消失类 |

| ID | 规则 |
|---|---|
| **M-32** | 所有 `Animatable` / `animate*AsState` 必须经 `WedoMotionPolicy` 取 spec，不得直接写 `spring()` |
| **M-33** | `WedoMotionPolicy.resolve(base: AnimationSpec): AnimationSpec` —— 动效关闭时返回 `snap()`（S1） |
| **M-34** | `AnimatedVisibility` 类必须显式给 `enter`/`exit`，动效关闭时用 `fadeIn()/fadeOut()`（S3）而不是空 |
| **M-35** | 装饰性动画（本计划内不存在，但保留条款）一律走 S2：不在组合中创建 |

### 3.7.3 双源门控

「动效开着」必须同时满足两个条件：

```
if (userMotionEnabled && systemAnimatorScale > 0f) → 正常动画
else                                              → S1/S3
```

| ID | 规则 | 理由 |
|---|---|---|
| **M-36** | 用户开关与系统 `ANIMATOR_DURATION_SCALE` 是**与**关系，不是或 | 用户在系统里关了动画，App 不该逆着来 |
| **M-37** | 系统值必须用 `ContentObserver` 监听，不能只在启动时读一次 | 用户可能切出去改设置再回来 |
| **M-38** | `ValueAnimator.getDurationScale()` 读不到时（部分 ROM）保守返回 0 → 视为关闭 | 宁可少动，不要逆用户 |
| **M-39** | 材质降级**不随动效开关变化** | 材质不是动画（V-68）。关动效后玻璃仍然是玻璃 |

M-39 是一条容易被搞错的边界：有人会觉得「关了动画就该关玻璃」。错。玻璃是**静态材质**，它不消耗动画预算；关掉它只会让界面变丑，不会让它变快。

## 3.8 动画中断与连续性

### 3.8.1 中断为什么是难点

用户手势是不讲道理的：拖到一半松手、松手立刻再按、快速连点、拖回原点。动画系统必须在这种输入下保持**位置连续**与**速度连续**。

**「位置连续」**好办：目标值改了就改。**「速度连续」**是难点——如果重新起一段动画且速度从 0 开始，会看到「顿一下再走」。

### 3.8.2 本项目的解法（不需要自研）

`Animatable.animateTo(targetValue, animationSpec)`：

- 内部以 `this.value` 为起点、`this.velocity` 为初速度构造新的 `SpringSimulation`;
- 速度继承是**默认行为**，不需要传参；
- 因此「拖到一半改目标」天然是连续的。

| ID | 规则 |
|---|---|
| **M-40** | 中断续跑一律用 `Animatable.animateTo` 重新设目标，**不得** `stop()` 后再 `animateTo()` —— `stop()` 会清零速度 |
| **M-41** | `block{}` 里只允许做「派生量的同步写回」，不得在 `block` 内改目标值（会自激） |
| **M-42** | 手势驱动期用 `snapTo`（跟手），松手后用 `animateTo`（自主运动）。两段之间不重置速度 |

M-40 是硬规则。`stop()` + `animateTo()` 是最常见的错误写法，因为它「看起来更安全」（先停再起），实际会丢掉速度，产生可见的顿挫。

### 3.8.3 快速连点

`wedoPress` 当前的写法是 `interactions.collectIsPressedAsState()` → `animateFloatAsState`。快速连点时，`pressed` 在 true/false 之间快速翻转，`animateFloatAsState` 每次改目标都继承速度 → 表现为「抖动而不是缩放」。

| ID | 规则 |
|---|---|
| **M-43** | 按压类动画增加「最小驻留」：进入按下后至少 80ms 才允许回落 |
| **M-44** | 最小驻留不得改变最终视觉（不得让按钮停在 0.97） |

M-43 的 80ms 是经验值，属设计起点。它的作用类似 FlClash 的 `_liftSnap = 0.975`（「手指抬起时若膨胀还没涨满 97.5%，先涨满才允许回落」），但更简单：本项目不做「必须先到某个值」，只做「至少待够一段时间」——因为本项目的按压只改 scale，从 0.97 回落不会产生「半程被掐断」的僵硬感，只有「抖动」问题。

### 3.8.4 手势与动画的所有权

| ID | 规则 |
|---|---|
| **M-45** | 同一时刻，同一属性只能有一个所有者（手势 或 动画），不得同时写 |
| **M-46** | 所有权切换必须发生在**同一帧**：`onDragEnd` 里先 `snapTo(最终位置)` 再 `animateTo(落点)` |

M-46 的落地：`HorizontalPager` 已经由框架处理了这个问题（`settledPage` 只在落定时回写，拖动过程不发散，见 `ScheduleScreen.kt:141-145` 的 `snapshotFlow` 写法）。**新增的手势不要绕过这个模式去自己写 `detectDragGestures`**，除非确实需要（如底栏高亮跟随）。

## 3.9 落点投影与吸附（M-30 段续）

### 3.9.1 为什么需要投影

甩动松手时，用户期望的是「页面滑到某个合理位置」，不是「滑到手指松开那一刻的速度衰减完的位置」。前者是**投影**，后者是**物理模拟**。

两者差别很大：快速甩动时，物理模拟会滑出几屏，投影只滑一格。

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **M-47** | 投影时长 | 100ms | 用当前速度外推 100ms 的位置作为落点 |
| **M-48** | 最大跨格 | 1 | 无论甩多快，一次最多跨一格 |
| **M-49** | 吸附阈值 | 段宽的 30% | 拖过 30% 即判为「要换」，否则回弹 |
| **M-50** | 触觉节流 | 每次跨格一次，不重复 | 同一次甩动只震一次 |

M-48 是关键：不限制跨格数，快速甩动会一次跳 5 周，用户根本不知道跳到了哪。限 1 格后，「甩得快」表现为「更快到达相邻周」，而不是「跳过」。

### 3.9.2 触觉

现状只有 2 处（`ScheduleScreen.kt:147-151` 换周落定、`:184` 长按课程）。

| ID | 规则 |
|---|---|
| **M-51** | 触觉必须与**事件**对齐，不与手指按下对齐 | 换周触觉在「落定」时震，不在「开始拖」时震 |
| **M-52** | 一次手势最多 2 次触觉（跨格 + 落定），不得逐帧触发 |
| **M-53** | 触觉受 `display.haptics` 门控（该开关在 P0 前也是死的） |

**M-51 的理由**：触觉是「确认」，不是「预告」。手指刚按下时用户还没做决定，此时震一下只是噪音。落定时震，才是在说「你换到第 5 周了」。

FlClash 研究 §A.5 记录过同样的结论（「触觉与透镜跨格事件同帧对齐，而非与手指按下对齐」）。本项目直接采纳。

## 3.10 布局与动画的关系（这是最容易做错的一层）

### 3.10.1 两个位置：layout 与 draw

Compose 里同一个「位移」有两处可写：

| 位置 | API | 是否触发 measure | 是否触发 draw | 精度 |
|---|---|---|---|---|
| **layout** | `offset { IntOffset }` / 自定义 `Layout` 的 `placeRelative` | ✅ 是 | 是 | **整数像素** |
| **draw** | `graphicsLayer { translationX = Float }` | ❌ 否 | 是 | **浮点（亚像素）** |

| ID | 规则 |
|---|---|
| **M-59** | 只有「影响其他元素排布」的位移才走 layout。纯视觉位移一律走 `graphicsLayer` |
| **M-60** | 需要亚像素精度的高刷动画，必须「layout 取整 + graphicsLayer 补余数」两段式 |
| **M-61** | `graphicsLayer` 的 `translationX/Y` 不得与 layout 位移**同时**作用于同一属性 | 会双倍位移 |

### 3.10.2 两段式的正确写法（`SegmentedSwitcher` 已验证）

```
值 = 弹簧输出（浮点，如 2.37 段）

layout 层：placeRelative(x = (值 × 段宽).toInt())     // 只负责「排在第几段」
draw   层：graphicsLayer { translationX = exact - exact.toInt() }  // 负责余数
```

为什么不能只用 layout：`toInt()` 把 2.37 变成 2，丢掉 0.37 段的位移 → 120Hz 下每帧丢一点，累积起来就是「一格一格跳」。

为什么不能只用 draw：`graphicsLayer` 的位移**不改变布局位置**，所以它能画出「在段 2 和段 3 之间」，但点击热区、无障碍焦点、`Layout` 的兄弟元素排布仍认为它在段 2。对纯视觉元素（高亮块）够用；对可点击元素不够。

→ **高亮块用两段式；可点击元素只用 layout 位移（宁可牺牲亚像素）**。

### 3.10.3 一个真实的反面案例

`WedoTabBar` 的隐藏用的是 `graphicsLayer { translationY = size.height * hideFraction }`（`:149`），并且被 `TabBarHideContractTest.kt:110-116` 钉死。

这**正确**：底栏隐藏是纯视觉位移，不需要改布局（底栏本来就浮在内容上方，内容区的底部留白由 `LocalNavExtraBottomPadding` 单独提供）。

如果哪天有人想「隐藏时也让内容区随之扩展」，那就变成了 layout 位移——但那就违背了「底栏常驻、不隐藏内容」的产品决策，且会撞 B-09。**不支持这个改法。**

### 3.10.4 材质动画不能走 layout

玻璃面板的「长出来」如果走 layout（改变高度），会导致：

- 每帧重新 measure 整棵子树 → 面板内的文字重新折行 → 看起来在抖；
- 捕获的离屏也要跟着每帧重建。

→ **材质动画一律走 draw 层**（`drawBehind` 里的裁剪矩形来自进度，不是布局高度）。

| ID | 规则 |
|---|---|
| **M-62** | 玻璃面板的展开收缩，布局高度**直接设为目标值**，视觉上的「长出来」由 draw 层的裁剪矩形 + alpha 完成 |
| **M-63** | 由此产生的「布局已撑开但视觉还没撑开」的间隙，用户不可见（因为面板底色透明） |
| **M-64** | 该间隙内的点击必须**穿透**到下方内容（不能用布局满尺寸的透明面板挡住） |

M-64 是容易忽略的可用性缺陷：一个「视觉上只有半高、布局上已满高」的面板，如果吃掉了下半部分的点击，用户会感觉「下面点不动」。

## 3.11 调参指南（「感觉不对」时查这张表）

弹簧参数一定会需要调。问题在于「感觉不对」是模糊的，而参数是具体的。这张表把模糊描述映射到具体旋钮。

**使用前提**：先确认不是层次错误。如果 L1 与 L2 搞混了，调任何参数都不会对。

| 你感觉到的 | 最可能的原因 | 调什么 | 调整方向 |
|---|---|---|---|
| 「太快，没看见」 | 阻尼太低或刚度太高 | 对应 M-ID 的 `k` | **降低** k（如 520 → 380），不要动 ζ |
| 「太慢，拖沓」 | 刚度太低 | `k` | **提高** k（如 380 → 520） |
| 「弹得太厉害，像坏掉了」 | 阻尼比太低 | `ζ` | **提高** ζ（如 0.40 → 0.55） |
| 「一点不弹，很硬」 | 阻尼比太高 | `ζ` | **降低** ζ（如 1.0 → 0.75） |
| 「跟手有延迟」 | 用了非 M-01 的弹簧 | 换 M-01 | 跟手必须 ζ1.0 / k10000 |
| 「松手后还在飘」 | 用了 M-01 做自主运动 | 换 M-03 / M-06 | M-01 没有「到位感」 |
| 「抖动」 | 中断时被 `stop()` 清零了速度 | 查 M-40 | 去掉 `stop()` |
| 「一格一格跳」 | layout 取整丢了亚像素 | 加 `graphicsLayer` 余数 | 见 §3.10.2 |
| 「几个部件不同步」 | 多根弹簧各驱动一部分 | 收敛到 M-20 单进度 | 见 §3.5 |
| 「整体像放大，不像材质」 | 派生量映射完全同步 | 错开映射区间 | 见 M-56（20%–30%） |
| 「拖起来像橡胶圈」 | 只做了 L1 缩放，没做 L2 反相 | 补 M-04 | 见 §3.2 |
| 「形变跟着位置一起抖」 | 形变弹簧驱动了位置 | 查 M-R3 | M-04 只能驱 `scaleX/scaleY` |
| 「连续点会抖」 | 缺最小驻留 | 加 M-43 | 80ms 起 |
| 「甩一下跳过好几个」 | 缺跨格限制 | 查 M-48 | 限 1 格 |
| 「关动画后还在动」 | 该处未接 `WedoMotionPolicy` | 查 §3.7.4 的 16 处 | 逐处补 |

### 3.11.1 调参的三条纪律

| ID | 纪律 |
|---|---|
| **M-65** | **一次只改一个参数**，且改完必须重新看完整交互，不看中间帧 |
| **M-66** | 改参数必须记进 `WedoSprings.kt` 的 KDoc（值 + 原因 + 日期），否则三个月后没人知道为什么是 0.55 |
| **M-67** | 不得为了让「某一帧」好看而改参数。以完整交互的观感为准 |

M-66 是血泪条款：`WedoMotion.kt` 现在只有一行「用户实测定参（高硬度+无回弹，MediumLow 拖沓不跟手）」，谁知道当初试了几版？

### 3.11.2 参数不得随便出的边界

有两类参数**不允许由实施者自行调整**：

| 类型 | 归属 | 理由 |
|---|---|---|
| M-R1..M-R3 的三条硬规则 | 架构层 | 违反即结构性缺陷，不是审美 |
| M-01（跟手）的 ζ/k | 架构层 | 跟手必须临界阻尼，任何 bounce 都会让拖动「追不上手指」 |

其余 M-ID 的数值都是**设计起点**，允许在真机上调，但必须留痕（M-66）。

**遗留问题**：

1. **M-27..M-31 无实测依据**，全部为设计起点。L2 形变是最需要真机调参的部分，必须由 VR-09（拖拽录屏 + 逐帧比对）后调整。
2. **M-03（settle，ζ0.55）的过冲幅度未量化**。过冲多少算「弹得好看」，无法纸面决定——VR-10 需要用户做「盲选两版」。
3. **M-43（最小驻留 80ms）是经验值**，`WedoPress` 的快速连点表现需要真机验证（VR-11）。
4. **§3.1.3 的亚像素范式只在一个组件上验证过**（`SegmentedSwitcher`，120Hz 真机）。推广到玻璃面板的滚动场景后是否仍成立，属 VR-08 的范围。
5. **M-39「材质不随动效降级」与卷 08 的降级策略可能冲突**：若某设备性能极差，是否需要「动效关 + 材质降」？当前结论是「材质降级只看设备能力（ADR-27），与动效开关正交」。若真机上出现「关动效仍然卡」，这条需要复审——列为 U-14。
