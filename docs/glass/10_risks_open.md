# 10 · 风险、依赖与未决事项

> 本卷定义**什么会出问题、出问题时怎么办、哪些事还没定**。
> **本卷不写**：参数（02/03/04）、组件（05）、模块（06）、阶段（07）、预算（08）、用例（09）。
> 上游：卷 01 `R1`、卷 08 的 `P-ID`、卷 09 的 C 类
> 下游：卷 11 的交付清单须含本卷的应急措施所需产物

## 10.1 本卷的三条写作纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **不编造概率**。严重度用「影响面 × 不可逆性」定性排序，不写「发生概率 30%」 | 无实测、无历史数据，概率是编的 |
| 2 | **每条风险必须对应到具体的 `Q-ID` / `VR-ID`** 作为监测手段 | 否则「监测」栏只能写「多留意」 |
| 3 | **应急必须可操作**。禁止「加强评审」「密切关注」这类空话 | 空话在真出事时等于没有 |

## 10.2 风险清单（R-01 … R-10）

### R-01 观感被否（最严重的一条）

| 项 | 内容 |
|---|---|
| **发生条件** | 玻璃做出来了、测试全绿，但用户看了说「不好看」。2026-09-27 已经发生过一次 |
| **影响范围** | 全部 P1–P6，可能整体回退 |
| **严重程度** | **致命**（唯一可能导致全盘作废的风险） |
| **预防** | ① `ADR-19`：G0 独立可交付，光学失败不拖累基础质感<br>② P1 阶段就做盲比（`VR-02`），不等最后<br>③ 不引入品牌色环境层（`D8` / `NG`）<br>④ 参数取自建，不照搬 FlClash（卷 04 §4.2） |
| **监测** | `VR-02`（G0 盲比，5 人中 4 人能指出「更有厚度」）；其后每阶段一次盲比 |
| **应急** | **两条路，必须选一条，不能都留着**：<br>**路 A**：回退到 G0-only（保留环境层 + 镀层），关掉所有 G1/G2/L2。产物：`GLASS_ENABLED=true` 但 `GlassQuota.maxG2=0`<br>**路 B**：完全回退到实色（`GLASS_ENABLED=false`），把 `docs/glass/` 整套归档为「已评估未采用」<br>选择判据：若 `VR-02` 通过而 `VR-12`（L2 差异）不通过 → 走路 A；若 `VR-02` 本身不通过 → 走路 B |

**R-01 的应急为什么必须二选一**：两条路的产物、文档、后续维护成本完全不同。留着「到时候再看」等于把决策推迟到最没有余裕的时刻。

### R-02 捕获管线掉帧 / 发热

| 项 | 内容 |
|---|---|
| **发生条件** | ① Bake 失效（每帧重录）② 包围盒过大 ③ 低端机 blur sigma 成本失控 |
| **影响范围** | P2 / P4 / P5；用户可感知的卡顿与耗电 |
| **严重程度** | 高 |
| **预防** | `O-03`（只在 `hasLiveConsumer` 录）、`O-11`（静止降 Bake）、`O-52`（滚动折叠 L1）、`GlassQuota`、`P-21`（宽屏 maxG2=1） |
| **监测** | `VR-05`（帧率对比）、`Q-50`（Bake 切换）、`Q-51`（全 G0 无捕获）、`P-05`（静止时 record 次数 = 0） |
| **应急** | 降 `GlassQuota.maxG2` → 若仍掉帧，G2 全降 G1 → 仍不行则回 G0。**不回总闸**（`A-20`：降级是少一点质感，不是回到改造前） |

### R-03 契约测试大面积红，导致有人删断言

| 项 | 内容 |
|---|---|
| **发生条件** | 改动碰到 `MainActivity` / `WedoTabBar` / `WedoWeekHeader` / `ImportWizard`，多处断言同时红 |
| **影响范围** | 全部既有 831 个测试的可信度 |
| **严重程度** | 高（一旦护栏被拆，后续所有「全绿」都不可信） |
| **预防** | `D9` / `ADR-22`：只允许窄化 1 条；卷 09 §9.7 的修改登记表；安全红线写明「不许删」 |
| **监测** | CI 的**测试数**：低于 830 即红灯（`P-0x` 的「测试数不低于 830」） |
| **应急** | 若发现有人删了断言：① 从 git 历史恢复该测试 ② 把改动方式改为「迁移断言位置」而非删除 ③ 在 `PATCH` 记录里留痕 |

**监测手段为什么是「测试数」而不是「测试全绿」**：删断言之后测试也是全绿的。只有数量能发现。

### R-04 课程块对比度崩塌

| 项 | 内容 |
|---|---|
| **发生条件** | 有人把 `lerpColor` 的 `alpha = 1f` 改成 `copy(alpha)`；或改了 `TINT_ALPHA`（0.55）；或 G0 的 tint 叠在课程色之上导致明度偏移 |
| **影响范围** | 全部 11 色 × 明暗 = 22 组；`A1` 品牌锚点；可读性 |
| **严重程度** | 高（直接伤可读性，且不会崩） |
| **预防** | `B-01`（CONTENT 底色不透明度不得降低）、`V-35`/`V-36`（取色阶段混合）、`Q-19b`（契约测试锁 `alpha == 1.0f`） |
| **监测** | `Q-31`（22 组数值表）、`Q-19b` |
| **应急** | 若 `Q-31` 红：**立即停 P1**，不得调 `TARGET_TEXT_CONTRAST` 迁就（那是把标准降下来）。回退到改动前的取色实现 |

### R-05 API 26–30 上「玻璃」退化成半透明色块

| 项 | 内容 |
|---|---|
| **发生条件** | L0 配方没做好，只有 tint 没有 rim/hairline 的组合；或用户以为「玻璃坏了」 |
| **影响范围** | 26–30 的全部用户（国内存量不小） |
| **严重程度** | 中（不影响功能，但影响口碑） |
| **预防** | `V-24`（L0 的双环补偿）、`V-28`/`V-29`（尺寸门槛）、卷 01 `G-03` 的盲比判据 |
| **监测** | `VR-01`（三档 API 截图并排） |
| **应急** | 若 L0 观感明显劣于改造前：**在 26–30 上直接 `GLASS_ENABLED=false`**（回到实色），而不是硬撑 L0 |

**R-05 的应急是分档关闭**，这是本计划里唯一允许「按 API 分段关」的地方。理由：26–30 上玻璃的收益本来就最小（无模糊），劣化时没有理由保留。

### R-06 Release 崩溃（proguard / 资源被 shrink）

| 项 | 内容 |
|---|---|
| **发生条件** | ① `proguard-rules.pro` 的 keep 规则仍是旧包名 `com.lingion.sleepy.**` ② `res/raw/liquid_glass.agsl` 被 `shrinkResources` 删除 |
| **影响范围** | release 变体的**全部功能**（Room 实体、`@Serializable`、L2） |
| **严重程度** | **高**（release 崩 = 不能发版） |
| **预防** | P0 的 `T-0.2`（改 keep 规则）、`O-49`（`tools:keep`） |
| **监测** | P0 门禁里已要求「一次 minify 构建 + 真机安装」；P6 前再跑一次 |
| **应急** | 若 release 崩：① 先确认是 keep 还是 shrink ② 用 `-keep class com.wedo.schedule.** { *; }` 临时兜底 ③ 定位后收窄 |

**这条的隐蔽性**：`isMinifyEnabled=true` 只在 release，debug 永远不崩。**如果 P0 不做一次 minify 构建，这个雷会一直埋到发版那天。**

### R-07 能力边界不一致（小组件没有玻璃）

| 项 | 内容 |
|---|---|
| **发生条件** | 用户装完新版，发现 App 内是玻璃、桌面小组件还是实色 |
| **影响范围** | 感知一致性；可能被当成 bug 反馈 |
| **严重程度** | 低（不是缺陷，是技术边界） |
| **预防** | `NG-01` 明确不改造；发布说明里讲清 |
| **监测** | 无（无法用测试监测「用户会不会觉得奇怪」） |
| **应急** | 在发布说明 / 应用内「关于」里写一句「小组件由系统 RemoteViews 渲染，不支持材质效果」 |

**这条不改代码，只改沟通。** 记录它是因为：不写清的话，三个月后会有人来问「为什么小组件没变」。

### R-08 未来迁 NavHost 导致离屏翻倍

| 项 | 内容 |
|---|---|
| **发生条件** | 有人为了「更规范」把 `OverlayScreen` 早退链换成 `Navigation-Compose` |
| **影响范围** | 离屏内存翻倍（下层页面保留在组合中，Host 不 dispose） |
| **严重程度** | 中（当前不发生，属未来风险） |
| **预防** | `NG-03` / `ADR-24` 禁止迁移；`A-11` / `A-12` 写明「若迁移必须补路由遮盖停止录制」 |
| **监测** | 无自动手段；靠 code review |
| **应急** | 若真的迁了：在 NavHost 的 `destination` 变化处补 `stage.stopRecording()` |

**这条是「给未来的人留的字条」**。当前无风险，但一旦有人动了导航结构，这条会救他。

### R-09 验收依赖外部（用户不回传证据）

| 项 | 内容 |

| **预防** | 卷 09 §9.11 的「最小可行验收集」（4 条决策树） |

### R-10 L2 白做（看不出差别）

| 项 | 内容 |
|---|---|
| **发生条件** | `VR-12` 盲比中 5 人 ≤ 2 人能分辨 L1 与 L2 |
| **影响范围** | 一个 shader 文件（约 140 行）+ 一个 API 33 分支 + 每次改动的双端对齐成本 |
| **严重程度** | 中（成本白付，但不影响交付） |
| **预防** | 卷 07 P4 的「三种失败处理」已含此判据；`O-29`（L2 只能 Bake）已限制其适用范围 |
| **监测** | `VR-12` |

**R-10 的应急「保留但关闭」而非「删除」**：删除的代价是「未来想重启要重写 140 行 AGSL + 一条契约测试」；保留的代价是「一个不被调用的文件 + 一个 `SDK_INT` 分支」。后者更便宜。

## 10.3 未决事项正文（U-01 … U-23）

`00_MASTER` §0.13 只有一句话。本节给出「为什么还没定」。

### 10.3.1 影响方案骨架的（优先定）

| ID | 未决 | 为什么还没定 | 倾向与反对理由 |
|---|---|---|---|
| **U-01** | 自动降档是否允许改用户设置 | 技术上能改，但属越权 | 倾向不改（`ADR-29`）。反对：用户可能希望「系统帮我调到最流畅」 |
| **U-02** | 画质偏好默认档（现 `balanced`） | 取决于 L1 在主流设备上的表现，未测 | 倾向 `balanced`。反对：低端机默认 `smooth` 体验更稳 |
| **U-05** | 课程色种子不一致（`courseName` vs `groupId`）是否纳入 | 属独立 bug，与玻璃正交 | 倾向纳入（玻璃化后色差更明显）。反对：会牵动小组件，扩大回归面 |
| **U-12** | L2 是否允许用户手动开启 | 若 `VR-12` 判「看不出差别」，手动开关是否还有意义 | 倾向保留（折腾选项）。反对：用户开了看不到效果会觉得是假的 |
| **U-23** | 15 个 `AlertDialog` 判 G0 是取舍还是限制 | 技术上可做 G1（快照），但必然一次可见跳变 | 倾向 G0。反对：若用户坚持「对话框也要玻璃」，必须接受跳变 |

### 10.3.3 未决事项的处理规则

| 规则 | 内容 |
|---|---|
| **X-1** | `U-01` / `U-02` / `U-05` / `U-12` / `U-23` 五项**必须在 P1 之前定**（它们影响参数表与降级链） |
| **X-2** | 其余可在实施中定，但**必须在 PATCH 记录里留痕** |
| **X-3** | 任何未决事项**不得在代码里以「暂时这样」的方式落地** | 那会让「未决」变成「事实标准」，再也改不动 |

**X-3 是本项目的一条既有教训**：`WedoDesign.kt` 的 `motion` 开关当初大概是「先加上，UI 以后再做」，结果 `WedoPreferences.write()` 生产零调用，一直假到今天。

### 10.4.1 两个「前置」类 VR 的特殊性

`VR-17` 与 `VR-18` 是唯一两个**必须在阶段开始前就验证**的项（其余都是阶段内验证）。

| VR | 位置 | 不过的后果 |
|---|---|---|
| `VR-18` | P1 开始前 | A-17 的写法若不成立，整个 `ui/glass` 的 API 隔离方案要换（可能是接口注入而非返回 `Any?`） |
| `VR-17` | P4 开始前 | AGSL 若不能编译，L2 整体作废，P4 直接跳过 |

**为什么它们前置**：它们验证的是「方案是否成立」，不是「参数是否合适」。方案不成立时，阶段内的所有工作都是白做。

### 10.4.2 VR 的执行边界

| 规则 | 内容 |
|---|---|
| **X-4** | 18 个 VR 中，`VR-17` / `VR-18` 是**阻塞项**（不过则阶段不能开始）；其余 16 个是**阶段项** |
| **X-5** | 阻塞项的验证方法可以极简（装个 demo APK 看崩不崩），不需要完整功能 |
| **X-6** | 16 个阶段项中，`VR-02` / `VR-05` / `VR-12` 是**决策项**（结果直接决定去留），其余 13 个是**调参项**（结果只影响参数） |

**X-5 的意义**：`VR-18` 不需要等 P1 做完才能验——写一个最小 example（一个 `@RequiresApi(33)` 返回 `Any?` 的函数 + 26 侧调用）装到 API 26 设备上看崩不崩，半天就能有结论。

## 10.6 最小可行验收集的缺口

卷 09 §9.11 给了「若用户只能做 4 条」的决策树。本节说明**只做 4 条会缺什么**：

| 缺的 | 后果 | 可接受吗 |
|---|---|---|
| `VR-01`（三档 API） | 26–30 的观感未验，`R-05` 无依据 | 可接受（26–30 收益本来就小） |
| `VR-07`（rim 方位比） | 侧面 rim 可能过暗或过亮，属调参 | 可接受 |
| `VR-08`（滚动亚像素） | 可能有跳格，但在 60Hz 设备上不明显 | 勉强可接受 |
| `VR-09`/`VR-10`（L2 形变、过冲） | P3 的手感未验，可能偏硬或偏软 | **不太可接受**（手感是「Q 弹」的全部） |
| `VR-14`（blur sigma） | 磨砂厚薄可能不对 | 可接受（属调参） |
| `VR-15`（refraction） | 边缘弯折可能过强 | 可接受（L2 默认关） |
| `VR-16`（1440p 质量） | 高分屏可能模糊不足 | 可接受（面小） |
| `VR-17`/`VR-18`（阻塞项） | — | **不可接受**（不过则方案作废） |

### 10.6.1 建议的最小集（6 条而非 4 条）

在卷 09 的 4 条基础上，加两条阻塞项：

| 序 | VR | 理由 |
|---|---|---|
| 0 | `VR-18` | 不验则 P1 无法开始 |
| 0 | `VR-17` | 不验则 P4 无法开始 |
| 1 | `VR-02` | 决定路线成不成立 |
| 2 | `VR-05` | 决定能不能用 |
| 3 | `VR-12` | 决定 L2 去留 |
| 4 | `VR-03` | 决定真玻璃做没做出来 |

**为什么 `VR-17`/`VR-18` 排在 1–4 之前**：它们是「零成本」的——写个 demo 装一次就知道，不需要完整功能。**花半天排掉两个「方案级」不确定性，比先做两个月再发现要划算得多。**
