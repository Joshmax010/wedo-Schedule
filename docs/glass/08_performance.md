# 08 · 性能、兼容性与降级策略

> 本卷定义**代价**：三条预算、怎么测、怎么降、在哪些设备上会退化成什么样。
> **本卷不写**：材质参数（02/03/04）、组件方案（05）、模块（06）、阶段（07）、验收用例细节（09）。
> 上游：卷 04（离屏数量与面积）、卷 06（模块与引用计数）、卷 07（灰度顺序）
> 下游：卷 09 的 Q-ID 引用本卷的 P-ID；卷 10 的风险按本卷的阈值设监测

## 8.0 一条前置声明（必须写在最前面）

**本卷不含任何实测数据。**

| 事实 | 后果 |
|---|---|
| 开发机无真机、无模拟器、无 AVD（`00_MASTER` `F-09`） | 拿不到一个真实的帧时间、内存占用、GPU 温度 |
| 仓库无 JankStats、无 macrobenchmark、无 baseline profile | 没有既有基线可比 |
| `dumpsys gfxinfo` 需要连接真实设备 | 同上 |

所以本卷所有数值分两类，**必须区分**：

| 类型 | 标注方式 | 可信度 |
|---|---|---|
| **建议目标** | 「建议目标：…」 | 推导得出，未经实测。**不是承诺** |
| **实测值** | 「实测：…（设备 X，日期 Y）」 | 由用户在真机上测出并回传 |

**任何写成本卷结论却没有标注来源的数字，都视为虚构。** 这条约束不是洁癖：一个假的「58fps」会让后续所有优化都建立在错误基线上。

## 8.1 三条预算及其推导

### 8.1.1 P-01 帧预算（玻璃的增量部分）

**推导过程（不是拍数字）**：

```
一帧的总预算
  60Hz  → 16.67 ms
  120Hz →  8.33 ms      （项目默认钉最高刷率，见 AppPrefs.kt:251）

玻璃改造允许占用的增量
  不能吃掉全部——内容本身（60+ 课程块、文字排版、滚动）也要用
  经验上「新增视觉效果」的合理上限是总预算的 15%
  → 60Hz: 2.50 ms
  → 120Hz: 1.25 ms

按玻璃一帧要做的事拆：
  ① record（重绘内容子树的包围盒）
  ② blur sigma（对离屏做一次高斯）
  ③ 合成 N 个面板（裁剪 + tint + rim + hairline）
  ④ （L2）shader 一次全屏 pass

四项的量级估计：
  ① 与「内容复杂度 × 包围盒面积」正相关
  ② 与「离屏像素数 × 核半径」正相关（半分辨率下是 1/4 的量）
  ③ 与「面板数 × 面板面积」正相关，但每块只是一次贴图
  ④ 与「屏幕像素数」正相关，与面板数无关

→ 结论：② 是最贵的一项，① 是波动最大的一项，④ 是唯一与面板数解耦但绝对量很大的
```

| ID | 项 | 建议目标 | 说明 |
|---|---|---|---|
| **P-01** | 玻璃的**增量**帧时间（60Hz） | ≤ 2.5 ms | 占 16.67ms 的 15% |
| **P-01b** | 玻璃的**增量**帧时间（120Hz） | ≤ 1.25 ms | 占 8.33ms 的 15% |
| **P-13** | 滚动 janky frame 占比（改造后 vs 改造前） | 劣化 ≤ 10%（相对值，非绝对值） | 绝对值取决于设备，相对值才是可比的 |

**为什么 P-13 用相对值**：不同设备的绝对 janky 率差异可达数倍（低端机 8%、旗舰机 1%）。要求「绝对值 < 3%」在低端机上永远不达标，在旗舰机上等于没约束。

### 8.1.2 P-02 离屏内存

**推导**：

```
最坏情况：1080 × 2400 物理像素
半分辨率（O-04 的 0.5×）→ 540 × 1200 = 648,000 像素
RGBA8888 = 4 B/px → 2,592,000 B ≈ 2.47 MB / 张

离屏张数上限
  嵌套深度 ≤ 2（O-14）→ 最多 2 张
  跨窗口 Snapshot 最多 1 张（O-85）
  → 最多 3 张

  2 张离屏: 4.94 MB
  + 1 张 Snapshot: 2.47 MB
  = 7.41 MB

加上位图池复用与临时分配的余量（约 1.5×）
→ 建议上限 12 MB
```

| ID | 项 | 建议目标 | 说明 |
|---|---|---|---|
| **P-02** | 玻璃相关离屏内存总量 | ≤ 12 MB | 2 张离屏 + 1 张快照 + 余量 |
| **P-09** | 低内存设备的离屏上限 | ≤ 6 MB | `isLowRamDevice` 为真时只留 1 张离屏、不留快照 |
| **P-10** | 长时间运行后的内存增量 | ≤ 5%（连续使用 30 分钟后） | 检测泄漏 |

**P-02 的计算有前提**：它假设屏幕不超过 1080p。1440p 屏上半分辨率是 720×1600 = 1,152,000 px → 每张 4.4MB，三张 13.2MB，**已超预算**。

→ 这就是 `O-05`（最大边长 2048）存在的理由：1440p 的 0.5× 是 720×1600，未超 2048，所以不触发再降。但 1600 > 1200，内存确实超了。

**处置**：`P-02` 的 12MB 需按「短边」重新表述——

| 修订 | 内容 |
|---|---|
| **P-02** | 玻璃相关离屏内存 ≤ **min(12 MB, 屏幕像素数 × 4 B × 3 / 4)** |

第二项即「半分辨率 × 3 张」的精确值。1080p 时是 7.4MB（约束为 12MB 那个），1440p 时是 13.2MB（约束为公式那个）——**1440p 上必须降张数**。

→ 由此得出一条降级规则：**1440p 及以上屏，嵌套深度强制降为 1**（只留 1 张离屏）。

### 8.1.3 P-03 record 面积比

**推导**：

```
底栏：52dp 高 × 全宽
  常见手机 360×800 dp → 52/800 = 6.5% 屏面积
  高屏 360×900 dp   → 52/900 = 5.8%

顶栏：44dp × 全宽 → 44/800 = 5.5%

两者合计约 12%（如果都 G2）

G2 的包围盒还会外扩 24dp（O-06） → 再增约 8%
→ 单个 G2 的实际 record 面积 ≈ 6.5% + 8% ≈ 14.5%
```

| ID | 项 | 建议目标 | 说明 |
|---|---|---|---|
| **P-03** | 单个 G2 面板的 record 包围盒面积 | ≤ 屏面积 15% | 与 `O-06` 的外扩配套 |
| **P-04** | 同屏同时录制的面板数 | ≤ 1（静止时） | `O-19` 已定：顶栏 G0、底栏 G2，所以静止时只有 1 个 |
| **P-05** | 静止时单帧 record 次数 | 0 | Bake 生效（`O-10`） |

**P-03 的 15% 与 P-02 的 12MB 是同一件事的两个面**：面积决定离屏大小，离屏大小决定内存。`O-05` 的 2048 边长是硬上限，`P-03` 是软配额。

## 8.2 怎么测（无 benchmark 模块时的可执行方案）

### 8.2.1 三个可用手段（按成本排序）

| # | 手段 | 成本 | 能测什么 | 不能测什么 |
|---|---|---|---|---|
| 1 | `adb shell dumpsys gfxinfo <pkg> framestats` | **零代码改动** | 每帧的 Draw / Prepare / Process 耗时、janky 率 | 一帧内的细分（record vs blur vs shader） |
| 2 | `Window.OnFrameMetricsAvailableListener`（API 24+） | 需写约 80 行 + 只在 debug | 同上，但可在 App 内自采、可打标签 | 仍需真机 |
| 3 | 手写 counter（`GlassDebug`） | 已有（`A-33`） | record 次数、离屏分配次数、降级次数、嵌套深度 | **不是时间**，是次数 |

### 8.2.2 手段 1：`dumpsys gfxinfo` 的标准流程

```
① adb shell dumpsys gfxinfo <pkg> reset      ← 清空基线
② 在设备上执行固定动作（见下表）
③ adb shell dumpsys gfxinfo <pkg> framestats ← 取 CSV
④ 解析 CSV 的 Draw / Prepare / Process 列，算 P50 / P90 / P99 与 janky 率
```

**固定动作必须可复现**，否则两次的 P90 不可比：

| 动作 | 时长 | 观察点 |
|---|---|---|
| 课表页静止（不碰屏幕） | 10 s | 应当接近 0 帧（无重绘） |
| 课表页纵向滚动到底再回顶 | 10 s | `P-13` 的主场景 |
| 横向翻 5 周 | 10 s | Pager + 底栏 LiveStrip |
| 打开/关闭课程详情 5 次 | 10 s | 跨窗口 Bake |
| 进设置页 → 展开一个分组 → 返回 | 10 s | G0 页面（应无捕获） |

**为什么第 1 项重要**：如果静止时仍有持续重绘，说明 Bake 没生效或引用计数没减（`A-9`）。这一项不过，后面所有数字都没意义。

### 8.2.3 手段 2：`OnFrameMetricsAvailableListener`

```kotlin
// 只在 BuildConfig.DEBUG 下注册
window.addOnFrameMetricsAvailableListener({ _, metrics, _ ->
    val total = metrics.getMetric(FrameMetrics.TOTAL_DURATION)     // ns
    val draw  = metrics.getMetric(FrameMetrics.DRAW_DURATION)
    val sync  = metrics.getMetric(FrameMetrics.SYNC_DURATION)
    // 按 GlassDebug 的当前档位打标签
}, handler)
```

| 规则 | 内容 |
|---|---|
| **P-06** | 该 listener **只能在 debug 变体注册**，release 下不注册 | 它有可观开销（每帧回调） |
| **P-07** | 采样必须按 `RenderTier` 分组统计 | 混在一起会得到「平均值」，掩盖 L2 的尖峰 |

P-07 是一条实践要点：L2 在滚动时折叠为 L1（`O-52`），若不分组，L2 的成本会被大量 L1 帧稀释，得出「L2 只贵 5%」的错误结论。

### 8.2.4 不能做的事

| 做法 | 为什么不行 |
|---|---|
| 用「肉眼看着不卡」当结论 | 违反 `SC-06`；且 `2026-09-27` 已证明「感觉」不可靠 |
| 在 `flutter test` 式的软件渲染上测 | 本项目是 Compose，无等价路径；软件渲染的数字与 GPU 无关 |
| 用 CPU profiler 的「火焰图」估 GPU 成本 | 混淆了 CPU 与 GPU |
| 引用 FlClash 的 SwiftShader 数字 | 平台不同、渲染器不同、面板数不同（卷 04 §4.2） |

**最后一条要特别强调**：FlClash 研究的 §E0.x 有大量数字（「菜单 render pass 从 17 降到 12.4」），那是 **SwiftShader 软件渲染**下的相对次序，作者自己也标注了「不能给真机价格」。**本计划不引用这些数字作为本项目的预期值。**

## 8.3 渲染开销的构成（按可优化性排序）

| 环节 | 成本量级 | 可优化手段 | 优化上限 |
|---|---|---|---|
| **record（重绘内容）** | 高 | 缩小包围盒、降分辨率（`O-04`）、静止时 Bake | **最大**：静止时降到 0 |
| **blur sigma** | 高 | 半分辨率、单次模糊多面板共用（L1 的「模糊一次裁 N 次」） | 大：分辨率减半即 1/4 量 |
| **shader（L2）** | 中高 | 只在静止时 L2、滚动折叠 L1（`O-52`） | 大：滚动时完全省掉 |
| **合成面板** | 低 | 减少面板数（配额） | 小 |
| **rim / hairline 绘制** | 低 | 无 | 几乎无 |

**排序结论**：优化重点在 ① record 的时机 与 ② blur 的分辨率，不在「少画几条 rim」。

这条结论对实施很重要：如果 P2 掉帧，**第一反应应该是查 Bake 是否生效**（`P-05` 是否为 0），而不是去简化 rim 的绘制。

## 8.4 降级策略：三层仲裁

### 8.4.1 仲裁顺序（`ADR-27`，不得改）

```
① 设备能力（RenderTier）     ← 硬约束，不可覆盖
② 用户偏好（QualityTier）    ← 用户可选，但受 ① 限制
③ 运行时配额（GlassQuota）   ← 系统自行裁决
```

| 规则 | 内容 |
|---|---|
| **P-08** | 设备能力为 L0 时，用户选 Fine 也只按 L0 渲染；界面上该档显示为「当前设备不支持」而非可选项 |
| **P-11** | 用户偏好为 Smooth 时，**不得**因为设备支持 L2 就偷偷升上去 | 
| **P-12** | 运行时配额可以**在阶段内**降档，但不得跨阶段升档（避免「配额抖回」） |

**P-11 的理由**：`Smooth` 是用户明确选择的「我要省电/我要流畅」。系统偷偷升档等于违背用户意图。这与 P-08 是同一个原则的两面：**用户的显式选择优先于系统的「为你好」**，但设备能力是物理事实，说不支持就是不支持。

### 8.4.2 三层降级的具体映射

| 层 | 触发条件 | 降级动作 | 恢复条件 |
|---|---|---|---|
| **L1 运行时降档** | 连续 `P-07` 帧慢帧 | G2 → G1 → G0 | 连续 3 秒正常帧（`P-19`） |
| **L2 阶段内降档** | 阶段门禁不过 | 该阶段功能整体回退（卷 07 的回退列） | 下一阶段重新评估 |
| **L3 全局关闭** | `GLASS_ENABLED = false` | 回到改造前的实色 | 改构建常量 |

| ID | 参数 | 建议目标 |
|---|---|---|
| **P-07** | 连续慢帧数阈值 | 5 帧（60Hz 下约 83ms） |
| **P-14** | 慢帧判定阈值 | 单帧 > 2 × `P-01` 的增量预算 |
| **P-15** | 观察窗口 | 30 帧滑动窗口，窗口内慢帧占比 > 20% 触发 |
| **P-19** | 恢复观察期 | 连续 3 秒（180 帧 @60Hz）正常后才恢复一档 |

**P-14 的「2 倍」是有意的**：单帧尖峰可能来自 GC、来自其他 App 抢 GPU、来自系统动画。要求「2 倍预算」才算慢帧，可以滤掉这些噪声。用 1 倍会把所有抖动都算成「玻璃的问题」。

**P-19 的「3 秒」也是**：升档比降档更需要谨慎。频繁升降会让用户看到材质反复变化，比一直低档更糟。

### 8.4.3 自动降档只观测不改设置（`ADR-29` / `U-01`）

| 规则 | 内容 |
|---|---|
| **P-16** | 自动降档**不得**写回 `QualityTier` 的用户值 | 用户下次进设置还看到自己选的值 |
| **P-17** | 降档必须记录到 `GlassDebug.quotaDowngrades`，且 release 下可被用户主动上报时附带 | 否则「卡」的反馈无法定位 |

**P-16 与 P-17 的配合**：用户看到的是「我的设置没变，但好像变淡了」；开发者看到的是「这台设备降了 37 次档」。两者各得其所，不互相干扰。

## 8.5 平台兼容矩阵

### 8.5.1 API 三段

| 区间 | 真模糊 | AGSL | 能做什么 | 强制降级 |
|---|---|---|---|---|
| **26–30** | ✘ | ✘ | G0 全配方（rim + 内高光 + hairline + 阴影） | `RenderTier.L0` |
| **31–32** | ✔ | ✘ | G0 + blur sigma（L1） | `RenderTier.L1` |
| **33+** | ✔ | ✔ | L1 + 折射/色散（L2，默认关） | 按 `QualityTier` |

| 规则 | 内容 |
|---|---|
| **P-17a** | 三段之外**不得**再细分（不按 ROM、不按 GPU 型号） | 无法验证的细分等于凭猜测 |
| **P-18a** | `isLowRamDevice` 为真时，无论 API 是几，**再降一档** | 低内存机的瓶颈常在内存带宽而非 API |

### 8.5.2 ABI 覆盖

项目出 3 个 ABI 包：`arm64-v8a` / `armeabi-v7a` / `x86_64`（`isUniversalApk = false`）。

| ABI | 关注点 |
|---|---|
| `arm64-v8a` | 主力，P-01/P-13 的基准 |
| `armeabi-v7a` | 老设备，**最可能出现「G0 都卡」的情况**（内存带宽低） |
| `x86_64` | 模拟器/少数平板，不代表真机 |

| 规则 | 内容 |
|---|---|
| **P-20** | `armeabi-v7a` 必须单独跑一次 `dumpsys gfxinfo` | 它的结果不能从 arm64 推断 |

### 8.5.3 屏幕密度与尺寸

| 项 | 关注点 |
|---|---|
| 密度 | 1dp 的物理像素数差异 → rim（1dp）在 ldpi 上会粗糙、在 xxxhdpi 上会极细 |
| 分辨率 | 1440p+ 触发「嵌套深度降 1」（§8.1.2 的修订） |
| 尺寸 | 平板/折叠屏**未适配**（无 `sw600dp` 资源）。玻璃在宽屏上的面积比会显著变大 |

| 规则 | 内容 |
|---|---|
| **P-21** | 宽度 > 600dp 时，`GlassQuota.maxG2` 强制为 1 | 宽屏上底栏面积可能达 20%，超 `P-03` |
| **P-22** | 平板/折叠屏属**未适配范围**，不承诺玻璃效果 | 与既有「无平板适配」一致，不新增承诺 |

**P-22 的意义**：不要在没验证过的屏幕形态上承诺效果。宽屏上「底栏浮在课表上」的观感与手机差异很大，且无法在本机验证。

### 8.5.4 系统设置的兼容

| 系统设置 | 影响 | 处理 |
|---|---|---|
| 移除动画（`ANIMATOR_DURATION_SCALE = 0`） | 所有 `animate*AsState` 跳变 | 走 `M-36` 双源门控 |
| 增大对比度（`HIGH_TEXT_CONTRAST_ENABLED`） | 无直接影响 | 走 `V-67`：强制 G0 + rim ×1.25 |
| 字号缩放 ≥ 1.3× | 面板高度可能撑开 | `V-69`：按内容撑开，不裁切 |
| 深色模式 | 材质参数整套切换 | `V-60`..`V-63` |
| 电池优化/省电模式 | 系统可能限制帧率 | **不处理**（不读省电状态，避免增加不可测分支） |

**最后一条的取舍**：读省电状态再降档听起来很合理，但引入了一个「无法在真机上穷举验证」的分支。**宁可少一个优化，不多一个未验证的路径。**

## 8.6 长时间运行稳定性

### 8.6.1 三类可能的泄漏

| 类型 | 载体 | 检测方式 | 处置 |
|---|---|---|---|
| **离屏未释放** | `GraphicsLayer` / `Picture` | `P-10` 的内存增量 | `O-64`..`O-66` 的释放顺序 |
| **Snapshot 未释放** | `ImageBitmap` | 打开/关闭面板 100 次后的内存 | `O-85` 只保留一张 + `release()` |
| **引用计数不归零** | `GlassStage.liveCount` | `P-05`（静止时 record 次数应为 0） | `A-9` 用 `DisposableEffect` |

### 8.6.2 长稳测试协议

| ID | 项 | 建议目标 |
|---|---|---|
| **P-23** | 连续使用 30 分钟后，玻璃相关内存增量 | ≤ 5% |
| **P-24** | 打开/关闭跨窗口面板 100 次后，内存不增长 | 增量 ≤ 2 MB |
| **P-25** | 连续滚动 10 分钟后，帧时间不劣化 | P90 劣化 ≤ 5% |

**P-25 是「热」的代理指标**：长时间滚动若导致降频，P90 会上升。本机无法测温，只能用帧时间间接推断。

### 8.6.3 页面切换的释放

`OverlayScreen` 的早退链（`MainActivity.kt:376-444`）让覆盖页与被覆盖页**不同时在组合中**，所以 Host 会自然 dispose（卷 04 §4.13.4）。

| 规则 | 内容 |
|---|---|
| **P-26** | 不得为了「保留捕获状态」而把覆盖页改成常驻 | 会破坏 `NG-03` 与内存模型（`A-11`） |
| **P-27** | 若未来迁 `NavHost`，必须补「路由遮盖时停止录制」 | 否则离屏内存翻倍（`R-08`） |

## 8.7 无障碍与减动效的性能含义

一个反直觉的事实：**减动效对性能几乎没有帮助。**

| 项 | 减动效开启后 | 影响 |
|---|---|---|
| 弹簧动画 | 全部 `snap()` | 省掉若干帧的动画计算，但动画计算占比极低 |
| 玻璃材质 | **不降级**（`M-39`） | 材质是静态绘制，与动画无关 |
| record / blur / shader | **完全不变** | 这些是「有没有材质」决定的，不是「有没有动画」 |

| 规则 | 内容 |
|---|---|
| **P-28** | 减动效**不得**作为性能降级手段被宣传或依赖 | 它省的成本可忽略，用它当「低端机优化」是自欺 |
| **P-29** | 真正的降级路径只有 `RenderTier` 与 `GlassQuota` | 与动效开关正交（`U-14`） |

P-28 值得单独强调，因为这是最容易产生误解的地方：很多产品文档会写「低端机自动开启省电模式（关动画）」，但**关动画不省电**——省电的是关材质。本项目把两者分开，是对的。

## 8.8 逐技术项开销分析（用户点名的六项）

§8.3 给了「按可优化性排序」，但还不够——实施时需要知道**每一项单独贵在哪、贵多少量级、什么条件下会失控**。本节逐项拆。

### 8.8.1 背景模糊

| 项 | 内容 |
|---|---|
| 实现 | 离屏录制 → `RenderEffect` 高斯（L1）或 shader 内 Vogel 盘采样（L2 的差额补足） |
| 成本量级 | **高**。与「离屏像素数 × 核半径」正相关 |
| 关键参数 | `O-30`（blur sigma）、`O-04`（0.5× 分辨率）、`O-31`（勾股差扣减） |
| 失控条件 | ① 全分辨率做模糊（4× 成本）② 对每个面板各模糊一次（N× 成本）③ sigma 过大（核半径线性增长） |
| 防护 | `O-04` 强制半分辨率；L1 的「模糊一次裁 N 次」（§4.3.4）；`O-30` 的 sigma 不超过面板短边的一半 |
| 不可优化点 | sigma 太小会看不出磨砂，太大则成本线性上升——**存在一个最优区间，调参不能越界** |

**半分辨率为什么只省 4× 而不是更少**：像素数是 1/4，而高斯核的半径按 dp 固定，在更少的像素上覆盖的「相对核半径」更大——理论上应该更贵。但 `O-31` 的勾股差扣减恰好抵消这部分：纹理已含的模糊在更粗的网格上覆盖更多内容，shader 只补差额。**两者相抵，净省接近 4×。**

### 8.8.2 离屏渲染

| 项 | 内容 |
|---|---|
| 实现 | `GraphicsLayer.record { drawContent() }` |
| 成本量级 | **高且波动最大**。与「内容复杂度 × 包围盒面积」正相关 |
| 关键参数 | `O-06`（外扩 24dp）、`P-03`（≤ 15% 屏面积） |
| 失控条件 | ① 包围盒包住整屏（面积 100%）② 内容里有 60+ 块（`CourseTableView`）③ 每帧都录（Bake 失效） |
| 防护 | `O-03`（`hasLiveConsumer` 才录）、`O-10`（默认 Bake）、`O-11`（静止时 G2 降 Bake）、`GlassQuota.maxG2` |
| 最坏情况 | 全屏 + 60 块 + 每帧 → 相当于「每帧重绘整个课表」两次。这就是为什么必须 `O-03` |

**离屏是唯一「不做也能活」的成本**：不录就没有玻璃（降 G0），界面仍然完整可用。所以它的降级最干脆——直接不录。

### 8.8.3 纹理采样

| 项 | 内容 |
|---|---|
| 实现 | L1 的 `drawLayer` 贴图；L2 的 `uContent.eval(coord)` |
| 成本量级 | **中**。与「采样点数 × 面板面积」正相关 |
| 关键参数 | shader 内的 Vogel 盘 tap 数（16 / 32 / 64 三档） |
| 失控条件 | ① tap 数按档展开时选错档（σ 大却用 16 tap）② 每像素多次采样（折射 + 色散 = 3 次） |
| 防护 | tap 数按 σ 分档（`≤2 → 16`、`≤3.5 → 32`、其余 64）；色散只在透镜上启用（`O-25`） |
| 命名注意 | **这不是「纹理采样」的性能问题，是「采样次数」的问题**。一张纹理采 1 次和 64 次差 64 倍 |

### 8.8.4 Shader（L2）

| 项 | 内容 |
|---|---|
| 实现 | `RuntimeShader` + `BitmapShader`，一次全屏 pass |
| 成本量级 | **中高**，但与面板数**解耦**（一次 pass 画所有面板） |
| 关键参数 | `O-15a`（面板表 ≤ 6）、SDF 求值次数 |
| 失控条件 | ① 每帧重建 `BitmapShader`（`toImageBitmap` 进滚动路径，`O-29`）② 面板表遍历用动态上界（AGSL 编译不过，`O-77`）③ 分支过多导致 GPU 占用率飙升 |
| 防护 | `O-28`（禁进交互路径）、`O-29`（L2 只能 Bake）、`O-78`（未用槽位填零矩形，避免分支） |
| 特殊性 | **L2 是唯一「做与不做差别可能看不出来」的成本**（`VR-12`）。所以它的验收标准里有「若看不出差别则永久关闭」这一条 |

### 8.8.5 复杂轮廓

| 项 | 内容 |
|---|---|
| 实现 | SDF 圆角盒 + 入深修正（`O-18`/`O-19`） |
| 成本量级 | **低**。纯算术，无采样 |
| 关键参数 | `O-19` 的 `traced` 带（只在线与高光带内做精确修正） |
| 失控条件 | ① 全面板都用精确路径求值（而非只在带内）② 任意轮廓（64 向 profile + Catmull-Rom）被滥用 |
| 防护 | `O-19`：**光学用圆角近似、线与高光用精确路径**——按可见性分配精度 |
| 本项目现状 | 面板形状全部是 `continuous()`（圆角盒 + 半径膨胀），**不需要**任意轮廓路径。64 向 profile 的能力保留但不用 |

**这一项是全套技术里性价比最高的**：SDF 修正的算术成本几乎为零，但缺了它，rim 与形状会错位 0.5dp，玻璃「边缘有光」的效果直接失效。

### 8.8.6 多层透明合成

| 项 | 内容 |
|---|---|
| 实现 | 面板按 z 序叠 tint / rim / hairline |
| 成本量级 | **低**。每块面板一次贴图 + 几次加色 |
| 关键参数 | 面板数（`GlassQuota`：G2 ≤ 3、G1 ≤ 2）、嵌套深度（`O-14` ≤ 2） |
| 失控条件 | ① 面板数不受限 ② 嵌套深度 3+（离屏张数翻倍 + 三次 tint 叠加导致灰化） |
| 防护 | `O-14`（深度 ≤ 2）、`O-15b`（超配额按面积倒序降档）、`P-21`（宽屏 maxG2 = 1） |
| 一个算术事实 | tint 0.62 叠 3 层后透射率只剩约 5%——**第三层在物理上已经不是玻璃了**（卷 04 §4.5.2） |

### 8.8.7 六项汇总

| 技术项 | 成本量级 | 可优化空间 | 失控后果 | 最有效的单一防护 |
|---|---|---|---|---|
| 背景模糊 | 高 | 大（半分辨率 = 4×） | 掉帧 | `O-04` |
| 离屏渲染 | 高（波动最大） | **最大**（静止降到 0） | 掉帧 | `O-03` |
| 纹理采样 | 中 | 中（tap 分档） | 掉帧 | σ 分档 |
| Shader | 中高（与面板数解耦） | 大（滚动折叠） | 掉帧 + 发热 | `O-29` |
| 复杂轮廓 | 低 | 小 | 边缘错位（不是性能） | `O-19` |
| 多层合成 | 低 | 小 | 灰化（不是性能） | `O-14` |

**读法**：前四项是「性能问题」，后两项是「正确性问题」。把后两项当性能问题去优化是白费力气——它们的成本本来就很低，出问题是因为**用错了**。

### 8.8.8 GPU / CPU 负载的测量

用户要求覆盖这两项。诚实结论：**本机无法测量，只能给方法**。

| 项 | 可用手段 | 局限 |
|---|---|---|
| CPU 负载 | `adb shell top -H -p <pid>`（看线程级占用）；Android Studio Profiler 的 CPU 时间线 | 看不到 GPU 侧；Compose 的渲染线程占用会与主线程混在一起 |
| GPU 负载 | `adb shell dumpsys gfxinfo` 的 `Process` 列（含 GPU 提交）；部分设备支持 `adb shell cat /sys/class/kgsl/kgsl-3d0/gpubusy`（高通） | **厂商相关**，非高通设备无此节点；且不同 GPU 驱动暴露的指标不同 |
| 帧时间 | §8.2.2 的 `framestats` | 最可靠，推荐 |
| 温度/降频 | 无法直接读；只能用「长时间运行后 P90 是否劣化」间接推断（`P-25`） | 间接指标 |

| 规则 | 内容 |
|---|---|
| **P-30** | CPU / GPU 负载**不作为门禁指标**，只作诊断参考 | 无法在多数设备上稳定读取，做成门禁会导致「有的设备过、有的设备读不到」 |
| **P-31** | 门禁只用「帧时间」与「内存」两项 | 两者都能通过标准手段读到，且与用户体验直接相关 |

**P-30 的取舍理由**：一个「在小米上能测、在华为上测不了」的指标，做成门禁等于给部分设备开后门。**宁可指标少一个，也不要一个不可靠的指标。**

**遗留问题**：

1. **`P-01` 的 15% 是经验值**，无实测支撑。若真机上 P1（纯 G0）就已经吃掉 15%，说明 G0 的绘制本身有问题——那要在 P1 阶段就查，而不是等到 P2。

5. **`P-10` / `P-23` / `P-24` / `P-25` 四项都需要长时间真机测试**，用户未必愿意配合。→ 卷 10 的 `VR-` 清单里标为「建议做，非阻塞」。
