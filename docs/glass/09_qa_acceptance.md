## 9.1 三类验证的边界（不得互相替代）

用户明确要求：不得用其中一种替代全部。三类的分工：

| 类 | 名称 | 能证明什么 | **不能**证明什么 | 执行者 |
|---|---|---|---|---|
| **A** | 自动化测试 | 逻辑正确、接线存在、参数矩阵符合预期 | **任何视觉观感** | 任何人（`testDebugUnitTest`） |
| **B** | 人工视觉审查 | 外观是否符合预期、边缘/颜色/层次是否成立 | 帧率、内存、长时间稳定性 | 任何人（看截图/录屏） |
| **C** | 仅用户真机 | 真实 GPU 下的观感、帧时间、热、手感 | — | **只有用户**（`VR-` 编号） |

### 9.1.1 为什么契约测试不能证明视觉

831 个既有单测里，大量是「读源码文本的契约测试」（`TestProjectFiles.kt:5-13`）。它们断言的是**源码里有没有那行字符串**，例如：

```kotlin
assertTrue(src.contains("LocalTabBarVisibilityState provides tabBarState"))
```

它能证明「接线在」，不能证明「玻璃看起来对」。

> **2026-09-27 的否决正是这么发生的**：当时「27 个测试全绿」，但观感被否。全部测试通过 + 用户说难看 = 测试测的东西与用户在意的东西不是同一个。

→ 这是本卷最重要的一条纪律：**A 类全绿不等于可交付**。B 类与 C 类必须各自成立。

### 9.1.2 三类的数量分配

| 类 | 条数 | 占比 |
|---|---|---|
| A（自动化，Q） | 47 | 53% |
| B（人工视觉，Q） | 30 | 34% |
| C（仅真机，`VR-`） | 12 | 13% |
| **合计** | **89** | 100% |

A 类占比最高是正常的（可重复执行），但 **B+C 必须占 45%**——本卷为 42/89 = 47%，达标。如果一份验收规范里 90% 都是自动化，它就是在用「跑得过」冒充「做对了」。

| 规则 | 内容 |
|---|---|
| **V-1** | 截图必须**放大到能看清 1dp 带**（通常 4× 以上），否则等于没看 |

V-4 的理由：一句「没问题」在三个月后无法复核；「边缘 1dp 亮带，顶部约 1/3 高度有内高光渐变」可以。

## 9.5 证据规范

### 9.5.1 每类证据的最小要求

| 类 | 证据形式 | 必须包含 |
|---|---|---|
| A | 测试报告 XML / 日志 | 测试名、断言数、通过数、失败详情 |
| B | 截图 / 录屏 + 判定说明 | 设备、系统版本、画质档、明暗、放大倍数、**看到了什么** |
| C | 同上 | 同上 + 用户确认（「我看过，符合」） |

### 9.5.2 截图/录屏的命名规范

```
Q-28_课程块rim_放大4x_arm64_API34_浅色_balanced.png
Q-54_长按到sheet_慢放0.25x_API34_深色_balanced.mp4
```

| 规则 | 内容 |
|---|---|
| **V-8** | 文件名必须含 `Q-ID` + 一句话内容 + 关键环境 | 否则半年后无法归档 |
| **V-9** | 证据目录按阶段分：`evidence/P0/`、`evidence/P1/`… | 与卷 07 的阶段一一对应 |

### 9.5.3 不可接受的证据

| 形式 | 为什么不行 |
|---|---|
| 「我试过了，没问题」 | 无法复核 |
| 缩略图（< 200px） | 1dp 的边缘根本看不见 |
| 单帧截图证明「动画流畅」 | 动画必须看连续帧 |
| 别的项目的截图 | 平台/参数都不同 |
| 我（Agent）自己描述的「效果」 | 本机无设备，任何「我看到」都是虚构 |

最后一条要写死：**本计划的执行者（AI）不得声称自己「看到了」任何视觉效果。** 所有视觉结论只能来自用户回传的证据或可复现的自动化渲染（如 golden，但本项目无此设施）。

## 9.6 失败处理分级

失败不是「全部重做」，按影响面分四级：

| 级 | 判据 | 处置 |
|---|---|---|
| **F1 阻断** | 崩、白屏、业务功能失效（导入/导出/提醒） | 立即停止，回退该阶段 |
| **F2 门禁** | 契约测试红、对比度不达标、配额超限 | 不进下一阶段，就地修 |
| **F3 观感** | 视觉不达预期但功能正常 | 记录，可在本阶段内调参重试**一次**；再不过则降档 |
| **F4 打磨** | 细节不一致（如某个对话框圆角差 1dp） | 记入技术债，可带到 P6 |

| 规则 | 内容 |
|---|---|
| **V-10** | F1 类必须**当天**回退，不得「先修修看」 | 业务功能是红线 |
| **V-11** | F3 类的「调参重试」**只有一次**机会 | 否则会陷入无限调参（`2026-09-27` 的教训之一） |
| **V-12** | F4 类必须登记到 `U-` 或技术债清单，不得口头带过 | 否则永远不做 |

**V-11 的设计理由**：观感调参没有收敛判据，容易无限循环。给一次机会 + 明确的「再不过就降档」出口，比「调到满意为止」更可能收敛。

## 9.11 最小可行验收集（若用户只能做 4 条）

现实中用户时间有限。若只能做 4 条 C 类，优先级如下：

| 优先 | Q-ID | 理由 |
|---|---|---|
| 1 | `VR-02`（G0 盲比） | 决定「这条路线成不成立」。不过则整体回退，其余不必做 |
| 2 | `VR-05`（帧率对比） | 决定「能不能用」。不过则降档，其余价值有限 |
| 3 | `VR-12`（L1 vs L2 差异） | 决定「L2 要不要保留」。不过则删 shader，省一份维护成本 |
| 4 | `VR-03`（首个 Bake 效果） | 决定「真玻璃有没有做出来」。不过则 P2 白做 |

**这 4 条构成一个决策树**：

```
VR-02 不过 → 整体回退到实色，其余全不做
VR-02 过、VR-05 不过 → 停在 G0，放弃 L1/L2
Q-89 过、Q-92 过、Q-98 不过 → 停在 L1，删 L2
四条全过 → 完整交付
```

这条树的价值：**它让「只做 4 条」也能得到明确结论**，而不是「验了 4 条，剩下 8 条不知道怎么办」。
