## 4.1 本卷要回答的唯一问题

**在 Compose 1.7.4 + minSdk 26 的约束下，「让玻璃真的采到背后的内容」这件事，到底怎么实现？**

前置事实（`00_MASTER` §0.3 已核）：

| 事实 | 后果 |
|---|---|
| Compose 1.7 无 `BackdropFilter` / 无 backdrop 语义 | 必须自己搭「父容器录制 → 重绘」链路 |
| `Modifier.blur` 与 `Modifier.graphicsLayer{renderEffect}` 只作用于**自身子树** | 不能「模糊背后的兄弟节点」 |
| `BlurEffect` 需 API 31+，低于 31 静默 no-op | 26–30 必须整体降级，不能 try/catch |
| `RuntimeShader` 需 API 33+，且 Compose 无包装类 | L2 要用 `android.graphics.RuntimeShader`，且必须独立文件（B-10） |
| 全仓渲染类玻璃代码 0 行 | 从零开始，无历史包袱也无既有范式 |
| `assets/`、`res/raw/` 不存在 | AGSL 需新建目录，无约定可循 |

## 4.2 为什么不能照搬 FlClash 的图集方案（ADR-17）

FlClash 的核心架构是「捕获图集（atlas）+ 按 sigma 分带（band）+ 按层升 level」。它能在跨平台 Flutter 上跑通，是因为它要处理**桌面/移动两套窗口系统、几十个面板、多层玻璃叠加**。

本项目的情况完全不同：

| 维度 | FlClash | wedo |
|---|---|---|
| 平台 | Flutter，多平台 | Compose，仅 Android |
| 同屏玻璃面板数 | 可达 10+（Dock + 顶栏 + 菜单 + 弹窗 + 开关 thumb…） | **配额限制 ≤ 5**（G2 ≤ 3、G1 ≤ 2） |
| 是否需要跨平台一致 | 是 | 否 |
| 是否需要处理窗口材质 | 是（macOS/Windows/Linux） | 否 |
| 团队规模 | 单作者 + 大量自研 | 单作者 |

**结论**：图集的分带复用、跨 sigma 共享、level 升层这三套机制，在「同屏最多 5 块玻璃」的场景下，收益远小于其复杂度（研究文档自己估计 1000+ 行）。

**本项目采用「单张离屏 + 面板表」**：

- 一个 Host 只有**一张**离屏；
- 所有玻璃面板共享这张离屏的同一份内容；
- 每块面板的差异（形状、入深、圆角）通过**面板表（uniform 数组）**传给 shader；
- 只有「玻璃叠玻璃」需要第二张离屏（嵌套深度 ≤ 2）。

这个方案的代价：无法做「每块面板不同模糊量」的精细化。收益：代码量从 1000+ 行降到约 300 行，且没有分带缓存的失效逻辑。

**这不是「简化版」，是「适配本场景的正解」。** 研究文档自己的结论也是「优先抄捕获图集架构，其次才是 shader 本体」——本项目抄的是**架构思想（先捕获、后光学）**，不是**具体机制（图集分带）**。

## 4.3 捕获管线：四段式

### 4.3.1 总览

```
Widget 树
  │
  ├─ 内容子树（页面 + 内容层）          ← ① 录制对象
  │
  └─ 玻璃槽（同级后画）
        │
        ▼
   ① Stage  ：Modifier.drawWithContent { stage.record { drawContent() }; drawLayer(stage.layer) }
        │        把整棵内容子树录进一个 GraphicsLayer
        ▼
   ② Replay ：把 stage.layer 以 RenderEffect(blur) 重绘回来
        │        此时「内容」已经在离屏里，且已模糊
        ▼
   ③ Paint  ：玻璃面板以 SDF 裁剪，叠 tint / rim / hairline
        │
        ▼
   ④ Optics ：（仅 L2）把②的结果作为 shader 的输入，做折射位移与色散
```

### 4.3.2 谁负责录制

**必须是 Host，不是面板。** 这是整个架构最关键的一处结构决定。

```kotlin
// 伪代码，示意结构；实际实现归卷 06
Box(Modifier.fillMaxSize()) {
    // 内容槽：会被录制
    Box(Modifier.drawWithContent {
        stage.record { this@drawWithContent.drawContent() }
        drawLayer(stage.layer)          // 先原样画出来
    }) {
        content()
    }
    // 玻璃槽：同级、后画、不在录制范围内
    glassLayer(stage)                    // 用 stage 的内容作纹理
}
```

三条不可违反的结构约束：

| ID | 约束 | 理由 |
|---|---|---|
| **O-01** | 玻璃面板必须是内容槽的**兄弟**，不是子节点 | 若是子节点，会被录进自己的纹理里 → 自采样（玻璃里出现玻璃自己） |
| **O-02** | 一个 Host 只有一张离屏；同 Host 内所有玻璃共享它 | 符合 ADR-17；也符合「同组玻璃读同一层背景」的物理直觉 |
| **O-03** | 只在 `hasLiveConsumer` 为真时录制，否则直通 | 纯 G0 页面（无 G1/G2）不应有任何离屏开销 |

O-03 是可测的性能闸门：卷 09 的 Q-51 会断言「全 G0 页面下 `debugLastCapture == null`」。

### 4.3.3 只在需要时录：`hasLiveConsumer`

| 条件 | 是否录制 |
|---|---|
| Host 内存在至少一个 G1 或 G2 面板，且其包围盒与可见区相交 | ✅ 录制 |
| 全部为 G0 或 FLOAT 不可见 | ❌ 直通（`drawContent()` 原样画） |
| `RenderTier == L0`（API < 31） | ❌ 直通（L0 不需要采样） |
| `GLASS_ENABLED == false` | ❌ 直通 |

「直通」的实现不是「画一遍空的东西」，而是**完全不装 `drawWithContent` 包装**——用 `if (needCapture) CapturingBox(...) else Box(...)`，避免每帧多一层 lambda 调用。

### 4.3.4 裁剪：L1 与 L2 的差别

| 档 | 做法 | 代价 |
|---|---|---|
| **L1**（API 31–32） | 把整张模糊后的离屏，用 `clipPath(panel.shape)` 逐面板裁一次再画 | 模糊只做**一次**（对整张离屏），裁剪 N 次（便宜） |
| **L2**（API 33+） | 不裁剪。把整张离屏作为 `BitmapShader` 输入 shader，shader 内用 SDF 逐像素判断「是否在面板内」 | 一次全屏 pass，N 块面板合并为一次绘制 |

**为什么 L1 可以「模糊一次、裁 N 次」**：模糊是逐图素的卷积，`blur(图像)` 的任意区域等于 `模糊(该区域 + 邻域)`。所以对整张图先模糊再裁，与先裁再模糊，结果在边界内一致（边界外需要邻域，整张模糊天然满足）。

**为什么 L2 不裁剪**：`clipPath` 会打断 shader 的连续采样域。折射需要「面板外的内容」作为采样源（边缘要把外面的东西弯进来），一裁就没了。

### 4.3.5 离屏参数

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **O-04** | 离屏分辨率 | 0.5× 物理分辨率 | 模糊是低频操作，半分辨率足够；4× 省内存 |
| **O-05** | 最大离屏边长 | 2048 | 超过则按比例再降 |
| **O-06** | 包围盒外扩 | 24dp | 给折射留采样余量（折射最大位移见 O-21） |
| **O-07** | 重录触发阈值 | 内容位移 ≥ 1 物理像素 | 亚像素位移不触发重录（这是 V-42 的根） |
| **O-08** | 亚像素停放 | 内容按**物理像素网格**对齐后再录 | 保证相同内容不因浮点偏移产生不同纹理 |
| **O-09** | 离屏格式 | RGBA8888 | 不用 565（会丢色阶，模糊后出现色带） |

**O-04 的 0.5× 与 O-08 的停放是配套的**：半分辨率下，1 物理像素的内容位移 = 0.5 离屏像素 → 必然触发重录；只有内容位移 ≥ 2 物理像素才真正改变图素。所以 O-07 的实际阈值应理解为「≥ 1 个**离屏**像素」，即 2 物理像素。

这个推导必须写清，否则实施者会按「1 物理像素」实现，然后在 120Hz 滚动中每帧重录。

### 4.3.6 与滚动的交互（本项目最频繁的场景）

底栏浮在课表网格上，用户滚动网格时底栏玻璃必须跟着变。这是全 app 唯一「内容真在栏下滚动」的位置（卷 01 §1.2.2 已指出）。

| 时刻 | 模式 | 重录频率 | 说明 |
|---|---|---|---|
| 静止 | Bake | 0 | 内容没变，不重录 |
| 滚动起始（第一帧） | 切 LiveStrip | 每帧 | `ScrollState.isScrollInProgress` 变 true |
| 滚动中 | LiveStrip | 每帧 | 只录底栏包围盒 |
| 滚动停止 | 120ms 后切回 Bake | 1 次 | 落定后补一次 |

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **O-50** | 切回 Bake 的延迟 | 120ms | 给惯性滑动留缓冲；太短会在惯性中反复切换 |
| **O-51** | LiveStrip 的录制高度 | 底栏高 + 2 × O-06 | 只需底栏自己的带，不需要全屏 |
| **O-52** | 滚动期间的 L2 折叠 | 立即（同帧） | 滚动开始时 `RenderTier` 临时降为 L1 |

**O-52 是硬性的**：L2 需要 `toImageBitmap()`（O-28/O-29），滚动中每帧调用必然卡死。这不是性能优化，是「能不能用」的问题。

衍生缺陷：滚动停止后从 L1 升回 L2，材质会有一次**可见跳变**（边缘从「平」变「弯」）。这是真实缺陷，登记为 VR-13。缓解手段只有两个：

1. 滚动停止后延迟 120ms 再升（O-50 同一个延迟），让跳变发生在用户注意力已离开屏幕时；
2. 若实测跳变明显，**底栏永久停在 L1**，L2 只用于静止的 G1 大面。

第二个选项是更可能的结论——FlClash 研究的实测也显示 L1/L2 的差异集中在边缘带，静止时才看得出。

### 4.3.7 与 `HorizontalPager` 的交互（横向翻页）

课表页是 `HorizontalPager`，横向翻周。翻页过程中：

| 时刻 | 玻璃怎么办 |
|---|---|
| 手指拖动中 | 页面内容在横向位移，底栏不动 → 底栏的 Bake 失效（下面内容变了）→ 切 LiveStrip |
| 松手惯性滑动 | 同上 |
| 落定 | 120ms 后切回 Bake |

**这里有一个与纵向滚动不同的坑**：`Pager` 会同时组合**相邻页**（预取），所以「底栏下方的内容」实际上是两页的拼接。

| ID | 规则 |
|---|---|
| **O-53** | 捕获的坐标系必须是**整屏坐标系**，不是「当前页的坐标系」 |
| **O-54** | `Pager` 的预取页必须被包含在捕获范围内 | 否则翻页瞬间底栏玻璃会出现「半块空白」 |
| **O-55** | 不得为「避免捕获两页」而关闭 Pager 预取 | 关闭预取会让翻页出现白屏，代价更大 |

O-53 的技术后果：`drawWithContent` 必须装在**包含 Pager 的那一层**（`ScheduleScreen` 的根 Column），不能装在单页内部。这条直接决定卷 06 里 Host 的摆放位置。

### 4.3.8 一帧之内的完整时序

实施时最容易搞错的是「谁在哪一帧做什么」。下面是单帧内的固定顺序，任何一步提前或延后都会导致「慢一帧」或「撕裂」。

```
① Composition      —— 状态变化触发重组。玻璃参数（GlassSpec）在此**已经算完**
                       ↑ 若在此阶段读 SDK_INT / isLowRam，每帧都要算 → 必须在 remember 里算一次

② Layout           —— 面板位置确定，得到本轮的面板矩形

③ Draw: content    —— 内容子树绘制进 stage.layer（record 块内）
                       ↑ 这里画的是「本轮尚未模糊」的原始内容

④ Draw: replay     —— stage.layer 经 RenderEffect(blur) 重绘回画布
                       ↑ 若 hasLiveConsumer == false，此步跳过，①的 record 也不发生

⑤ Draw: glass      —— 每块 FLOAT 面板：
                       (a) 取 ④ 的模糊结果
                       (b) 按 SDF / clipPath 裁剪
                       (c) 叠 tint（V-10/V-11）
                       (d) 叠 rim（V-40..V-43）
                       (e) 叠 hairline（V-22/V-23）
                       (f) L2 额外：把 ④ 作 shader 输入做折射/色散

⑥ Draw: shadow     —— 阴影最后画（V-34：阴影不进捕获）
```

| ID | 规则 |
|---|---|
| **O-69** | `GlassSpec` 的解析（含 `isLowRamDevice` 查询）必须发生在 ① 之前的 `remember` 里，**不得**在 ③④⑤ 内 |
| **O-70** | ③ 与 ④ 必须在**同一帧**内完成。跨帧就是「玻璃里是上一帧的背景」，即一帧延迟 |
| **O-71** | ⑤ 必须读 ④ 的**本轮**结果，不得读缓存（除非是 Bake 模式） |
| **O-72** | ⑥ 在 ⑤ 之后，且**不进入** stage.layer |

O-70 是这套方案相对 `BackdropFilter` 的核心优势。`BackdropFilter` 会终结当前 render pass 并把玻璃拖后一帧——本方案通过「先录后放」在同一帧内闭环，没有延迟。

O-69 是一个具体的性能陷阱：`isLowRamDevice` 是 `ActivityManager` 查询，虽不慢但不该每帧做。`wedoGlassSpec`（`WedoGlassTokens.kt:151-156`）当前**已经在 `remember` 里**做了这件事——这个写法是对的，扩展签名时不要把它挪出去。

### 4.3.9 与 `CompositionLocal` 的接线

捕获需要跨层级共享「这个 Host 的离屏」。项目无 DI（`WedoApp.get()` 手写单例），只能用 `CompositionLocal`。

| ID | 规则 |
|---|---|
| **O-73** | `LocalGlassStage` 由 Host 提供，默认值为 `null`（表示「不在 Host 内」） |
| **O-74** | 面板读 `LocalGlassStage.current`，为 `null` 时**自动降 G0**（而不是崩或白屏） |
| **O-75** | `LocalGlassDepth` 与 `LocalSurfaceClass` 同理由 Host 提供，默认 `0` / `CONTENT` |

O-74 覆盖了一个真实场景：**组件被用在 Host 之外**（如某个页面忘了包 Host，或 Preview 里单独渲染）。此时组件不应崩溃，应退化为 G0 —— 因为 G0 不依赖任何上下文。

这条也是单测友好性的来源：`WedoGlassTokensTest` 可以脱离 Compose 环境测 `buildGlassSpec`，就是因为它不读 `CompositionLocal`。

### 4.3.10 与 `WindowInsets` 的关系

底栏用 `navigationBarsPadding`（`MainActivity.kt:449: navBarBottom`）。捕获时：

| ID | 规则 |
|---|---|
| **O-56** | 捕获范围包含系统栏区域（因为 insets 是布局的一部分），但玻璃面板的绘制矩形**不含**手势条区域 |
| **O-57** | 手势条区域的底色由 `WedoBackground` 直接提供，不经过玻璃 |

理由：手势条区域如果也有玻璃，等于把材质延伸到系统 UI 边界，视觉上会与系统的导航条「打架」；且部分 ROM 会在该区域叠加自己的遮罩，叠加后颜色不可控。

## 4.4 三模：Bake / LiveStrip / Hold（ADR-28）

### 4.4.1 为什么需要三种模式

「每帧重录」在静止时是纯浪费，在滚动时是必需。三种模式的差别是**重录频率**。

| 模式 | 重录时机 | 适用 | 成本 |
|---|---|---|---|
| **Bake** | 面板**打开时**录一次；内容版本号变化时重录 | G1 大面（Sheet / Picker / Dialog） | 极低（一次） |
| **LiveStrip** | 每帧，但只录包围盒 | G2 条带（底栏 / 顶栏） | 高（每帧） |
| **Hold** | 面板沿**已知路径**移动时不重录，路径结束后补一次 | G1 沿固定路径（如 Sheet 上滑过程中） | 低 |

### 4.4.2 模式选择矩阵

| 条件 | 模式 |
|---|---|
| 面板静止，且下方内容也静止 | **Bake** |
| 面板静止，但下方内容在动（滚动） | **LiveStrip**（若为 G2）/ **Bake + 失效重录**（若为 G1） |
| 面板在动，路径不可预知（跟手拖拽） | **LiveStrip** |
| 面板在动，路径可预知（开合动画） | **Hold** |

| ID | 规则 |
|---|---|
| **O-10** | 默认 Bake，**不要默认 LiveStrip**（ADR-28） |
| **O-11** | G2 在**滚动容器不滚动**时，降为 Bake；滚动开始的那一帧切 LiveStrip |
| **O-12** | Hold 只在「开合动画」期间使用；动画结束必须补一次 Bake |
| **O-13** | 任何模式下，若 `RenderTier == L0`，不录制（走 G0 配方） |

O-11 是一个容易被漏掉的优化：底栏在页面静止时完全不需要每帧录。只有用户滚动时才有内容变化。

### 4.4.3 Bake 的失效条件

| 失效源 | 检测方式 |
|---|---|
| 下方内容滚动 | `ScrollState.value` 变化 |
| 数据变化（课程增删） | 数据版本号 |
| 主题切换 | `darkTheme` 变化 |
| 尺寸变化（旋转、分屏） | `onSizeChanged` |
| 面板自身移动 > 1dp | 位置差 |

**版本号设计**：`GlassContentVersion = hash(scrollValue, dataVersion, darkTheme, size)`。Bake 时记录该值，比对不等则重录。

不用 `snapshotFlow` 监听每个状态，用一个整数哈希更省——Bake 的重录本来就不频繁，哈希碰撞（不同状态同哈希）的概率可忽略，且碰撞只会导致「该重录没重录」，下次还会触发。

## 4.5 分层与嵌套（玻璃叠玻璃）

### 4.5.1 只有两层

| 层 | 内容 | 谁读它 |
|---|---|---|
| **Level 0** | 页面内容（BASE + CONTENT） | 页面级 Host 的玻璃 |
| **Level 1** | Level 0 的合成结果（含已合成的玻璃） | 浮层级 Host 的玻璃 |

| ID | 规则 |
|---|---|
| **O-14** | 嵌套深度 ≤ 2。第三层禁止 | 三层玻璃会「三重发灰」，且离屏数变 3 张 |
| **O-15** | 同层玻璃**不读同层其他玻璃** | 两块并列玻璃互不影响，读同一份背景 |
| **O-16** | 内层 Host 的 content 槽必须包含外层已合成的结果 | 否则浮层玻璃读不到底栏玻璃 |

### 4.5.2 为什么必须禁止第三层

三层玻璃叠加时，每层都加了 tint（V-10 浅色 0.62）。视觉上：

- 1 层：tint 0.62 → 38% 透射
- 2 层：0.62 + 0.62×0.38 → 14% 透射
- 3 层：0.62 + ... → 5% 透射

第三层实际已经是「几乎不透明的一块」，玻璃的意义完全消失，只剩成本。**这不是审美判断，是算术。**

### 4.5.3 与本项目实际场景的对应

| 场景 | 深度 | 是否允许 |
|---|---|---|
| 课表页：底栏浮在网格上 | 1（页面级） | ✅ |
| 课表页：详情 Sheet 浮在网格上，底栏仍在下方 | 2（Sheet 是浮层级） | ✅ |
| Sheet 内再弹一个 Dialog | 3 | ❌ 违反 O-14 |
| WeekPicker（全屏 Dialog）内再浮东西 | 2 | ✅（Picker 是浮层级，内部不再嵌套） |

第三种场景（Sheet 内弹 Dialog）真实存在：`CourseDetailSheet` 里点「删除」会弹 `AlertDialog`。**解法不是加深嵌套，而是让 Dialog 读 Level 0**——因为 Dialog 是全屏遮罩 + 居中卡片，它背后是 scrim，不是 Sheet 的内容。

这条判断写进卷 05 的 L-14 / L-20。

### 4.5.4 跨窗口：Sheet / Dialog / Picker 是另一棵树

这是本卷最晚发现、但影响面最大的一条。

**事实**：Android 上 `ModalBottomSheet`、`AlertDialog`、`Dialog` 三者都渲染在**独立窗口**里。

| 组件 | 实现 | 独立窗口 |
|---|---|---|
| `ModalBottomSheet`（Material3 1.3.0） | `ModalBottomSheetDialog` / `ModalBottomSheetWindow` | 是 |
| `AlertDialog`（Material3） | `BasicAlertDialog` → `Dialog` | 是 |
| `Dialog`（`WeekPicker` 用） | `androidx.compose.ui.window.Dialog` | 是 |

**后果**：§4.3 的捕获管线（`GraphicsLayer.record` + `drawWithContent`）只作用于**同一个窗口的图层树**。独立窗口有自己的一棵树，看不到主窗口的图层。所以「弹出面板上的玻璃实时采到底下页面」——**结构上不存在这条路径**，不是参数问题。

**唯一可行替代：跨窗口 Bake。**

```
① 主窗口在面板打开前，对内容区调一次 toImageBitmap()
② 把这张位图作为面板窗口内玻璃的背景纹理
③ 面板内的玻璃在这张纹理上做 blur sigma + rim + tint
```

这在光学上等价于 `Bake`（`O-10`）：静态背景，磨砂与高光照做。而面板打开时下方本就被 scrim 盖住且不可交互，所以**语义上无损失**。

| ID | 规则 |
|---|---|
| **O-81** | 跨窗口玻璃**只能**用跨窗口 Bake，禁止指望实时采样 |
| **O-82** | 快照必须在**目标窗口出现之前**拍，否则拍到的是「已盖上 scrim 的画面」 |
| **O-83** | 快照按 `O-04` 降采样（0.5×），避免每次开面板分配全尺寸位图 |
| **O-84** | 快照失败（OOM / 主窗口正在销毁）→ 降 G0。不重试、不阻塞打开 |
| **O-85** | 快照只保留**一张**（最近一次）。同时存在两张即泄漏 |

### 4.5.5 预拍窗口：有「按住期」就有时间

`toImageBitmap()` 是 suspend，最快一帧。若「点开瞬间」才拍，用户会看到 `G0 → 一帧后 → G1` 的材质跳变。

**解决办法是利用已有的时间窗**：`WedoCourseActions` 与 `CourseDetailSheet` 都由**长按**触发（`ScheduleScreen.kt:182-185`），长按本身有 300–500ms 的按住期，足够完成一次快照。

| 触发方式 | 预拍时机 | 结果 |
|---|---|---|
| 长按课程块 | `onLongClick` 同帧开始预拍 | 面板出现时快照已就绪，无跳变 |
| 点「分享」 | 按钮 `pressed = true` 时 | 有一次点击时长可用 |
| 点日期开 `WeekPicker` | 顶栏区域按下时 | 同上 |
| `AlertDialog` | **无预兆** | 只能 G0，或接受一帧跳变 |

| ID | 规则 |
|---|---|
| **O-86** | 有按住期的面板必须预拍；无按住期的**优先 G0 而不是「先 G0 再跳 G1」** |
| **O-87** | 预拍触发点放在 `onLongClick` / `pressed` 变化处，**不得**放在面板 Composable 的 `LaunchedEffect(Unit)`（那已是面板在开的时刻） |

O-86 的取舍理由：**一次材质跳变比「一直不做玻璃」更糟**。跳变会让用户注意到「这里有东西在变」，而玻璃的价值恰恰是「不引人注意地增加质感」。

→ 直接后果：15 个 `AlertDialog` 全部判 G0（卷 05 的 L-20），是**主动放弃**而非能力不足。

## 4.6 几何：SDF 与面板表

### 4.6.1 面板表（`GlassPanelTable`）

L2 的 shader 需要知道「屏幕上有哪几块玻璃、各自什么形状」。这份数据以 uniform 数组传入。

| 字段 | 类型 | 说明 |
|---|---|---|
| `rect` | `vec4` | 面板矩形（left, top, right, bottom），逻辑 px |
| `corner` | `float` | 圆角半径 |
| `bevel` | `float` | 斜面入深（O-16） |
| `refraction` | `float` | 折射深度，负数表示凸透镜（O-20） |
| `dispersion` | `float` | 色散强度（O-23） |
| `rimAlpha` | `float` | 来自 V-12 |
| `hairlineAlpha` | `float` | 来自 V-13 |
| `tint` | `vec4` | 预乘 alpha 的 tint 色 |

| ID | 参数 | 设计起点 |
|---|---|---|
| **O-15a** | 面板表最大条目 | 6 |
| **O-15b** | 超出时的处理 | 按包围盒面积**倒序**取前 6；其余降为 G0 |

**为什么是 6**：配额上限是 G2 ≤ 3 + G1 ≤ 2 = 5，留 1 个余量给过渡期（一个面板正在关闭、一个正在打开）。6 是 2 的幂附近的经验上界，也为将来放宽配额留口。

### 4.6.2 形状求值

| ID | 参数 | 内容 |
|---|---|---|
| **O-16** | bevel | L1 大面 20dp / L2 透镜 5.5dp / 条带 12dp |
| **O-17** | 入深计算 | `rise = 1 - clamp(inset / bevel, 0, 1)` |
| **O-18** | SDF 主体 | 圆角盒距离场 + 解析法线 |
| **O-19** | 轮廓修正带 | 只在 `traced = hairlineWidth + rimWidth` 带内用精确路径 |

**O-19 的取舍很重要**：圆角盒 SDF 与项目实际的 `continuous()`（squircle 近似）在长边入角处最大差约 1.8% 半径。这个差在「光学量」（折射位移）上不可见（因为折射读的是更深的区域），但在「线与高光」上可见（rim 只有 1dp 宽，错 0.5dp 就露馅）。

→ **按可见性分配精度**：光学用圆角近似，rim 与 hairline 用精确路径。这与 FlClash 研究的做法一致（其 shader 也是「光学用圆角、线与高光用超椭圆八分体」），但本项目不需要八分体拟合——因为项目的形状是 `continuous()` 近似，本身就是圆角盒 + 半径膨胀，可以直接在带内做解析修正。

## 4.7 折射与色散

### 4.7.1 普通面板（凸出）

| ID | 参数 | 内容 |
|---|---|---|
| **O-20** | refraction | 60dp（会被 `min(refraction, halfMinor)` 钳制） |
| **O-21** | 位移公式 | `depth = min(refraction, halfMinor) × (1 - sqrt(1 - rise²))`；`shift = -normal × depth` |
| **O-22** | 采样点 | `point + shift` |

**形状直觉**：`1 - sqrt(1 - rise²)` 是一个「根部平、近边缘陡」的曲线。所以：

- 面板中央：`rise ≈ 0` → `depth ≈ 0` → 不弯折；
- 边缘：`rise → 1` → `depth → refraction` → 最大弯折。

结果：**边缘一带把背后内容挤压并镜像**，中央几乎不动。这就是「液态玻璃」与「毛玻璃」最本质的差别——不是把背景弄糊，是把背景**弯**过来。

### 4.7.2 透镜（凹入）

| ID | 参数 | 内容 |
|---|---|---|
| **O-23** | 负折射 | -4.3dp |
| **O-24** | 负折射位移 | `shift = normal × |refraction| × smoothstep(0, bevel, inset) × (1 - smoothstep(bevel, halfMinor, inset))` |

负折射的分布是「边缘 0、bevel 处满、再向中心衰减」——形成一圈**被向外拉开**的环带，与普通面板的「向内挤压」方向相反。

**同一个公式、一个符号位，两种相反的光学器件。** 这是本项目唯一用到负折射的地方（L2 的透镜态，见卷 05 的 L-02 选中高亮）。

### 4.7.3 色散

| ID | 参数 | 内容 |
|---|---|---|
| **O-25** | dispersion | 透镜 6.5，其余风格 0 |
| **O-26** | 分离采样 | R/B 沿 `normal.yx × 0.5 × dispersion` 反向偏移各采一次，G 用原位；alpha 取三者最大 |
| **O-27** | 分离范围 | 入深 10dp 内满强度，7dp 后衰减 |

**色散只给透镜，不给任何其他面板。** 理由：色散是「厚玻璃边缘的棱镜效应」，只在**强曲率 + 薄边缘**上可见。给大面积薄板加色散，会得到「彩虹边」，看起来像渲染错误。

**O-25 的 6.5 是自建值**，不等于 FlClash 的 6.5（数值巧合）。本项目的透镜应用面积比 FlClash 的 Dock 透镜小得多（底栏高亮块 vs 一整个 Dock），同样的 dispersion 在更小的面积上会更刺眼，实际应在 VR-12 中下调。

### 4.7.4 L2 的输入限制（这是最硬的约束）

`RuntimeShader` 的输入只有两条路：

```
setInputShader(String, android.graphics.Shader)
setInputBuffer(String, android.graphics.BitmapShader)
```

**没有任何「读取屏幕 / 下层兄弟节点」的 API。**

所以 L2 的离屏内容必须先变成一个 `Bitmap`：

```
GraphicsLayer ──toImageBitmap()──> ImageBitmap ──> BitmapShader ──> RuntimeShader
                     ↑ suspend，会分配位图
```

| ID | 规则 |
|---|---|
| **O-28** | `toImageBitmap()` **禁止**出现在交互路径（B-11）。只允许 Bake 兜底、golden 抓帧、分享截图三处 |
| **O-29** | L2 的离屏转位图**只能在 Bake 时刻**做一次；LiveStrip 模式下一律降为 L1 |

O-29 是 ADR-28 的技术根因：**L2 与 LiveStrip 在技术上互斥**。不是「性能不够所以不做」，是 `toImageBitmap()` 是 suspend 且分配位图，放进每帧路径必然卡顿 + GC 抖动。

→ **L2 的实际适用范围**：静止的、Bake 模式的面板。也就是 G1 大面（Sheet、Picker、Dialog），以及**滚动停止后的底栏**。

底栏在滚动中必须降 L1（§4.4.2 O-11），落定后再升回 L2 —— 这个升降会带来一次可见的「材质跳变」，是个真实缺陷，登记为 VR-13。

## 4.8 磨砂、tint 与 Veil

### 4.8.1 磨砂在哪里做

| 档 | 磨砂位置 | 参数 |
|---|---|---|
| **L0** | 无磨砂 | — |
| **L1** | 离屏录制时由 `RenderEffect` 一次性模糊 | O-30 |
| **L2** | 同 L1，shader 只做「差额补足」 | O-31 |

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **O-30** | blur sigma（L1） | G1 大面 12dp / G2 条带 2.5dp | 与 `WedoGlassTokens.BLUR_CARD=20`、`BLUR_NAV=30` 不同——那两个是「环境取色范围」，不是真模糊 |
| **O-31** | sigma 差额补足 | `sqrt(max(σ² − texelσ², 0))` | 纹理已含的模糊要先扣掉，否则双重模糊 |
| **O-32** | 二次磨砂（rim 附加） | `frost = σ + rimBlur × rise²` | 越靠边越糊，模拟厚玻璃边缘散射 |
| **O-33** | rimBlur | 透镜 1.5dp / 其余 0 | 只在透镜上有 |

**O-31 的勾股差是必须的**：离屏已经按 O-30 模糊过，如果 shader 再按同样的 sigma 模糊一次，实际模糊量是 `sqrt(σ² + σ²) ≈ 1.41σ`，比设计值大 41%。用勾股差扣掉已含部分，才是精确的。

### 4.8.2 tint 与采样的关系

| 档 | tint alpha | 作用 |
|---|---|---|
| **G0**（不采样） | V-10：浅 0.62 / 深 0.48 | 假装有一层玻璃 |
| **G1 / G2**（采样） | V-11：浅 0.18 / 深 0.22 | 微调色相，不遮盖真实背景 |

**V-10 与 V-11 的落差是设计意图，不是笔误**（卷 02 §2.4.2 已说明）。若 G1 用了 G0 的 0.62，采到的真实背景被自己的染色盖住 62%，等于白做。

### 4.8.3 Veil：匀色遮罩不画进捕获

**问题**：Dialog 的 scrim（半透明黑遮罩）如果画进捕获，面板每帧都要重拍（因为 scrim 在面板下方）。而且 scrim 是完全均匀的，模糊它毫无意义。

**解法**：把「均匀铺满槽位的 scrim」从捕获中剔除，改为把其颜色作为 uniform 传进 shader，在玻璃合成时叠加。

数学依据：**匀色模糊后仍是自身**。所以「先模糊 scrim + 内容」在数学上等价于「模糊内容 + 叠加 scrim」。

| ID | 条件 | 内容 |
|---|---|---|
| **O-34** | 必须匀铺满槽位 | 局部渐变不能剔除 |
| **O-35** | 不得有效果叠加（如 scrim 上还有模糊） | 有叠加则不可分 |
| **O-36** | 不得被更窄的裁剪约束 | 裁剪会破坏「匀铺」前提 |
| **O-37** | 任一条件不满足 → 老老实实画进捕获 | 正确性优先 |

**代价**：满足 O-34..O-36 时，Dialog 的捕获从「每帧」降到「开合两次」。这与 FlClash 研究的菜单 hold 机制同源（其菜单 render pass 从 17 降到 12.4）。

## 4.9 rim 与「类 Fresnel」

### 4.9.1 必须说清的一件事：本项目没有真 Fresnel

真 Fresnel 需要**视向量 V** 与**法线 N**，计算 `pow(1 - |dot(V, N)|)`。

本项目：

- **没有视向量**（正交投影，相机固定在 z 轴方向）；
- **没有环境图 / 天空盒**；
- **没有设备姿态输入**（不读陀螺仪）。

所以「反射」这一维度**完全缺失**。看到的「光泽」全部来自：

1. rim 程序光（法线朝向调制）
2. 按压 glow（触点位置调制）
3. 内高光（固定顶部）

| ID | 规则 |
|---|---|
| **O-38** | 代码与文档**不得**把 rim 称为 Fresnel。唯一合法说法是「法线驱动的 rim」 |
| **O-39** | 不得声称有「环境反射」。若需描述，用「程序化高光」 |

这不是抠字眼。`WedoGlassTokens.kt:18-21` 的头注释已经列过「不承诺」的能力清单，本卷要显式取代其中两项（RR-03），但**不能顺带把不存在的东西说成存在**。

### 4.9.2 rim 在 shader 内的计算

| ID | 参数 | 内容 |
|---|---|---|
| **O-40** | facing 函数 | 普通面板取法线竖直分量的幂函数组合（`rise² → rise¹⁶` 混合）；透镜取 `smoothstep(0.65, 0.95, |normal.y|)` |
| **O-41** | band | `1 - inset / rimWidth`，高光只活在 `rimWidth` 内（V-20） |
| **O-42** | tail | 以 4.5dp 向内拖一条极弱长尾，权重 0.17（仅 G1 大面） |
| **O-43** | 混合比 | `rimAdded = 0.38`：38% 用加色（`plus`），62% 用 `screen` |

**O-43 为什么不能纯 screen**：纯 screen 在浅色 tint 上会把 rim 削成「一圈平白」。近四成改为加色，才能「把浅色按钮也抬亮」。这与 FlClash 的观察一致，但 0.38 是本项目自定的起点。

**O-42 的 4.5dp tail 只在 G1 大面上启用**：条带（底栏 52dp 高）的 rim tail 会占据近 9% 的高度，看起来像「上边缘发霉」。

| L0 vs L1 | **最大差异**：背景是否可见、是否有纹理 | 同场景截图（VR-01） |
| L1 vs L2 | 边缘内容是否弯折、是否有色散 | 同场景截图 + 放大边缘（VR-12） |

**L1 vs L2 的差异可能小于预期**。FlClash 研究的实测（§E0.6）显示：standard（对应 L1）与 ultra（对应 L2）的静止画面差异**只集中在透镜与 pill 区域，regular/menu 面几乎为 0**。

→ 本项目的预期同理：**L2 的收益主要在「边缘 10px 带」**，不在整块面板。若真机盲比看不出差别（VR-12），L2 应当**默认永久关闭**，只作为「折腾选项」保留。

## 4.11 uniform 契约：用测试锁顺序

### 4.11.1 为什么这是个真问题

FlClash 研究的 §8 明确指出其最大耦合风险：

> shader 与 Dart 的 uniform 顺序靠人工对齐（frag 头注释与 `_look()` 顺序），改一处漏一处即静默错位。

本项目同样会遇到：Kotlin 侧按顺序 `setFloat`，AGSL 侧按顺序声明。**顺序错一位，所有参数整体偏移一位，画面「看起来像玻璃但处处不对」**——这是最难查的一类 bug，因为它不崩、不报错，只是丑。

### 4.11.2 解法：单一顺序源 + 文本契约测试

| ID | 规则 |
|---|---|
| **O-44** | uniform 顺序**只有一个源**：`GlassUniforms.kt` 里的 `object` 常量数组（名字 + 类型 + 槽位） |
| **O-45** | AGSL 文件头必须包含一段**自动生成的注释块**，逐行列出 `// 0: uSize (vec2)` … |
| **O-46** | 文本契约测试（Q-04）断言：AGSL 注释块的行数、顺序、名字 与 `GlassUniforms` 数组完全一致 |
| **O-47** | 任何一方增删 uniform，另一方不改则测试红 |

O-46 是本卷最重要的工程手段。它把「靠人眼对齐」变成「CI 会红」。

**为什么不用反射 / 代码生成**：项目无 KSP 用于此类场景的既有设施，引入代码生成会让构建复杂化。生成一段注释块 + 文本断言，是成本最低的可行解。

### 4.11.3 顺序约定

| 段 | 内容 |
|---|---|
| 0–3 | 尺寸与时间（`uSize`、`uTime`、`uDpr`、`_pad`） |
| 4–11 | 全局光学（refraction、bevel、saturation、brightness、contrast、dispersion、blurSigma、veilAlpha） |
| 12–15 | 全局色（tint、rimColor、hairlineColor、glowColor） |
| 16–23 | 面板表（每面板 8 项 × 6 面板 = 48 项，超过单个 vec4 数组上限时拆多组） |

**这个分段不是随意的**：先放全局量，后放面板表，是为了让「只有一个面板」的常见情况可以只上传前 16 项（省一次数组上传）。

### 4.11.4 AGSL 不是 GLSL：五处必须提前知道的差异

本项目要写的是 **AGSL**（Android Graphics Shading Language，Skia SkSL 的一个方言），不是 FlClash 用的 Impeller GLSL 变体。两者语法相近，但以下五处不同，**踩了会编译不过或结果全错**：

| # | 差异 | GLSL 写法 | AGSL 写法 |
|---|---|---|---|
| 1 | 采样输入纹理 | `texture(uTex, uv)` | `uniform shader uContent; ... uContent.eval(coord)` |
| 2 | 入口函数 | `void main()` + `gl_FragColor` | `half4 main(float2 fragCoord)` + `return` |
| 3 | 精度限定 | 可选 | **必须**：`half` / `float` 要显式选 |
| 4 | 循环边界 | 可动态 | **必须是编译期常量**（bounded loop） |
| 5 | 提前退出 | `discard` | **不支持**，只能用 `return` 返回全透明 |

| ID | 规则 |
|---|---|
| **O-76** | 采样一律用 `uniform shader` + `.eval()`，不得假设有 `texture()` |
| **O-77** | 所有循环必须写成固定次数（如 `for (int i = 0; i < 6; i++)`），不得用 uniform 作上界 |
| **O-78** | 面板表遍历必须用 O-15a 的常量 6 作上界，未使用的槽位填零矩形 |
| **O-79** | 不得用 `discard`；面板外区域返回 `half4(0)` 并把 alpha 置 0 |
| **O-80** | 精度选择：坐标与颜色用 `half`，SDF 距离与法线用 `float`（`half` 在长距离上精度不足） |

**O-77 / O-78 是硬性的**：AGSL 的循环上界必须是编译期常量，这是 SkSL 的编译器限制。若按「遍历实际面板数」写（`for (i < panelCount)`），编译直接失败。

O-78 的「填零矩形」是个实用技巧：未使用的面板槽位填一个「远离屏幕的零尺寸矩形」，SDF 判定自然返回「不在面板内」，不需要额外的分支。

**O-80 的精度选择容易被忽略**：`half` 是 16 位浮点，在 0–1 范围内精度约 1e-3；但 SDF 距离值可能达到几百 px，`half` 在这个量级上精度只有 ~0.1px，边缘会出现台阶。所以距离与法线必须用 `float`。

### 4.11.5 无法在本机验证的部分

| 项 | 为什么不能验证 | 归属 |
|---|---|---|
| AGSL 能否编译 | 需要真机 GPU 驱动 + Impeller/Skia 后端 | VR-17 |
| 折射位移的实际观感 | 只有像素级抓帧能验，本机无设备 | VR-15 |
| `RuntimeShader` 在 API 33 上的行为 | 同上 | VR-12 |
| 半分辨率离屏的模糊质量 | 需在 1440p+ 设备上看 | VR-16 |

**这四项必须在 P4 开始前完成小规模验证**（卷 07 的 P4 前置条件），不得直接进主线。这是全计划里唯一「不做前置验证就会白干」的地方。

## 4.12 资源与 API 隔离

### 4.12.1 文件布局（ADR-26 / B-10）

| 文件 | 最低 API | 职责 |
|---|---|---|
| `ui/glass/GlassCapability.kt` | 26 | **纯函数**：`resolveRenderTier(sdkInt, isLowRam, quality)` |
| `ui/glass/GlassSpec.kt` | 26 | 数据类 + `buildGlassSpec(...)` 纯函数 |
| `ui/glass/WedoGlassSurface.kt` | 26 | 公开 Modifier，内部按 tier 分发 |
| `ui/glass/GlassCapture.kt` | 26 | Host + Stage + `rememberGraphicsLayer` |
| `ui/glass/GlassBlur.android.kt` | **31** | `BlurEffect` 的包装，独立文件 |
| `ui/glass/GlassShader.android.kt` | **33** | `RuntimeShader` + `BitmapShader`，独立文件 |
| `res/raw/liquid_glass.agsl` | — | AGSL 源码 |

| ID | 规则 |
|---|---|
| **O-48** | `@RequiresApi(31)` / `@RequiresApi(33)` 代码**必须**在独立文件，且不得被 26 的类**静态引用**（只能通过 `SDK_INT` 分支 + 反射或接口注入） |
| **O-49** | AGSL 文件必须加 `tools:keep`，防 `shrinkResources` 误删 |

**O-48 的技术根因**：`RuntimeShader` 类在 API 26–32 的设备上**不存在**。同文件内即使有 `if (SDK_INT >= 33)` 分支，类加载器在**类校验阶段**就会因为找不到 `RuntimeShader` 而抛 `NoClassDefFoundError`——不是运行时分支能救的。

这条在 `01_goal_decisions.md` §1.2.1 已列为 B-10，本卷给出落地方式。

**O-49 的坑**：release 开了 `isMinifyEnabled=true`（`app/build.gradle.kts:32`），`res/raw/*.agsl` 若无引用会被 shrink 掉，然后在运行时 `loadShader` 失败。而 `_GlassProgram` 类的一次失败会**永久标记 `_failed`**（FlClash 也有同一机制），导致整个 L2 永久失效且无任何提示。

→ 必须加 `tools:keep="@raw/liquid_glass"`，且 P6 前必须有一次 minify 构建 + 真机安装（R6）。

### 4.12.2 AGSL vs 内联字符串

| 方式 | 优点 | 缺点 |
|---|---|---|
| `res/raw/*.agsl` | 可被 IDE 高亮、可独立测试 | 需 `tools:keep`，加载是 IO |
| Kotlin 内联字符串 | 无资源依赖，不会漏 keep | 无语法高亮，字符串转义难读，编译期不可查错 |

**决策：用 `res/raw`**。理由：AGSL 有 400+ 行，内联字符串的维护成本过高，且无法在 CI 里做 lint。`tools:keep` 是可控的一次性配置。

## 4.13 失败模式与降级

玻璃是「锦上添花」的功能，任何失败都不允许让 App 不可用。**每一条失败路径都必须有明确降级，不能崩、不能白屏、不能静默无效果。**

### 4.13.1 五类失败

| # | 失败 | 触发条件 | 降级 | 是否可恢复 |
|---|---|---|---|---|
| F1 | shader 加载失败 | `loadShader` 抛异常 / 资源被 shrink | **永久**降 L1 | ❌ 进程内不可恢复 |
| F2 | `RenderEffect` 不支持 | `SDK_INT < 31` / `isShaderFilterSupported == false` | 降 L0 | ✅ 跟随设备 |
| F3 | 离屏创建失败 | `OutOfMemoryError` / 尺寸超限 | 降 G0（不采样） | ✅ 下次尝试 |
| F4 | 面板表溢出 | 同屏玻璃 > O-15a（6） | 面积最小的降 G0 | ✅ 每次重算 |
| F5 | 闪烁 / 跳像素 | 亚像素停放失效 | 降 L1 + 增大 O-07 阈值 | ✅ 配置可调 |

### 4.13.2 F1：为什么必须「永久」降级

`loadShader` 的失败在同一个进程内**一定会重复**——资源缺失是静态事实，不会因为重试而变好。而每次尝试都在 UI 线程做同步加载（FlClash 的 `_GlassProgram.request()` 有同样的注释）。

| ID | 规则 |
|---|---|
| **O-58** | 首次失败即置 `failed = true`，之后不再尝试；进程重启才重置 |
| **O-59** | 失败必须写日志（`Log.w`），但**不得**弹窗打扰用户 |
| **O-60** | 失败后 `RenderTier` 从 L2 降到 L1，界面仍完整可用 |

O-58 的「永久」是性能决定，不是偷懒。若每次面板出现都试一次，一块 400 行 shader 的编译在低端机上可能耗时 50–100ms，每次都是一次卡顿。

### 4.13.3 F3：离屏 OOM 的处理

离屏是一个 `GraphicsLayer`，尺寸由 O-04/O-05 决定。最坏情况（2048×2048 RGBA8888）= 16MB。低端机可能分配失败。

| ID | 规则 |
|---|---|
| **O-61** | 离屏创建包在 `try/catch (OutOfMemoryError)` 里 |
| **O-62** | 捕获失败 → 该 Host 内所有玻璃降 G0，并在 `WedoGlassDebugState` 里记录 |
| **O-63** | 降级后**不得**自动重试超过 1 次/分钟 | 否则会陷入「失败-重试-失败」的抖动 |

O-63 是需要经验的：一个每帧重试的 OOM 循环会让 App 直接 ANR。限频是必要的。

### 4.13.4 释放（这是最容易被漏掉的一处）

离屏、`Picture`、`Shader` 三者都会持有引用。**不释放即泄漏**。

| ID | 规则 |
|---|---|
| **O-64** | 面板离开图层树（`onDispose`）时，释放其捕获句柄 |
| **O-65** | 面板被路由/覆盖页遮盖时（`OverlayScreen` push 后），Host 应停止录制并释放离屏 |
| **O-66** | shader 对象持有最后采样的纹理 → 释放顺序必须是「先解绑纹理，再释放 shader」 |

O-66 的顺序问题是 FlClash 研究的 §4.6 明确记录过的坑（「shader 会持有最后采样的图，不释放即泄漏——代码注释明示此坑」）。本项目的 `RuntimeShader` 同样持有 `BitmapShader` 输入。

**O-65 与现有导航结构的耦合**：本项目用 `OverlayScreen` 早退链（`MainActivity.kt:376-444`），覆盖页与被覆盖页**不同时存在于组合中**。这意味着覆盖页 push 时，被覆盖页的 Host 会自然 `onDispose` —— 释放是自动的，不需要额外逻辑。

**这是「早退链」这个看似原始的结构带来的意外好处**：如果用 `Navigation-Compose` 的 back stack，下层页面会保留在组合中，Host 不会 dispose，离屏会一直占着。→ 反过来说，如果将来有人要迁移到 NavHost（NG-03 已禁止），必须补上「路由遮盖时停止录制」，否则内存会翻倍。

### 4.13.5 降级链的完整顺序

```
理想：L2 + G2 + LiveStrip
  ↓ F1（shader 失败）
L1 + G2 + LiveStrip
  ↓ F2（无 RenderEffect）
L0 + G2（无采样，等同 G0 + 加强 rim）
  ↓ F3（OOM）
G0（全配方，无采样）
  ↓ F4（面板超配额）
面积最小者 G0
  ↓ GLASS_ENABLED = false
今日实色路径（零分支残留）
```

| ID | 规则 |
|---|---|
| **O-67** | 每一级降级都必须是**外观变化**，不是**功能丧失**。降级后不能出现「按钮点不动」「文字看不见」 |
| **O-68** | 降级状态必须可观测（`WedoGlassDebugState`），供 QA 与用户反馈排查 |

**遗留问题**：

1. **O-30 的 blur sigma（12 / 2.5）无实测依据**。这两个值决定「磨砂厚度」的观感，必须真机调（VR-14）。
2. **O-20 的 refraction 60dp 是从 FlClash 的默认基线推导的**，本项目的面板尺寸不同，实际值可能在 30–60 之间。VR-15。
3. **O-43 的 rimAdded 0.38 是起点**，浅色 tint 上可能需要降到 0.25。
4. **§4.10.4 的预判（L1 vs L2 差异有限）来自 FlClash 的实测**，不能直接等同于本项目。若 VR-12 证实「看不出差别」，L2 应永久关闭 —— 这个决策点在 P4 结束。
5. **O-04 的 0.5× 分辨率**在 4K 屏上会让离屏达到 2048 上限并触发 O-05 的再降，实际模糊质量可能不足。需在 1440p+ 设备上验证（VR-16）。
6. **AGSL 的可用语法子集未验证**。FlClash 的 shader 是 Impeller 的 GLSL 变体，与本项目要写的 AGSL 不是同一方言。`smoothstep` / `mix` / `dot` 等基础函数通用，但纹理采样与分支限制可能不同 —— 这是 P4 的第一个技术风险，见 VR-17。
