# 02 · 全局视觉系统改造

> 本卷定义**静态视觉**：颜色、透明度、边缘、阴影、圆角、字图与材质的协调、明暗与复杂背景。
> **本卷不写**：blur sigma / refraction / bevel / dispersion（归卷 04 的 O-ID）、弹簧与时长（归卷 03 的 M-ID）、逐组件选型（归卷 05）。
> 上游：卷 01 的 G-/B-/SC-ID
> 下游：卷 04 的光学数值必须在本卷定义的几何与透明度基底上成立；卷 05 只引用 V-ID

---

## 2.1 本卷要解决的四个真实问题

改造前的视觉体系不是「不好看」，是**四个具体的结构性缺陷**。每一条都对应本卷的一个章节。

| # | 缺陷 | 证据 | 本卷对应 |
|---|---|---|---|
| 1 | 背景是纯色，玻璃无内容可采 | `WedoShell.kt:56-59`，`#F2F2F7` / `#000000` | §2.3 |
| 2 | 只有 4 档 alpha，无法表达「材质透明」与「内容透明」的区别 | `Theme.kt:325-337`，65 处引用 | §2.4 |
| 3 | 全库只有 1 处阴影，界面「贴」在纸上，无空间层级 | `SettingsCards.kt:93` | §2.7 |
| 4 | 12 个二级页各自 `Scaffold(containerColor)` 把底色重涂一遍，浮层无处可采 | 各 `*Screen.kt` | §2.2 + §2.6 |

第 4 条尤其致命：它意味着即使做出正确的捕获管线，底栏之外的任何浮层采到的都还是纯色。**这是必须先修的结构问题，不是视觉参数问题。**

## 2.2 三层结构的升级：从「语义分层」到「可判定分层」

`DESIGN_SPEC_V2.md:33` 定义了三层：

```
控件层（Control）—— 玻璃材质 / 强调色 / 导航
内容层（Content）—— 实色 surface / 课程色块
基底（Base）—— 页面背景
```

这个分层在**语义上是对的**，但三个问题让它无法直接执行：

1. **「控件层」与「内容层」的边界靠人判断**——设置页的分组卡（`SettingsCards`）到底算控件还是内容？它既是容器又是可点击项。
2. **没有「浮层」这一层**。Sheet / Dialog 是浮在内容之上的，与常驻的 tab bar 不是同一类。
3. **没有说明层与层之间的采样规则**——控件层能不能采内容层？内容层能不能采基底？

### 2.2.1 升级后的三层（对应 `SurfaceClass`）

| 层 | 标识 | 判定标准（可机械判定） | 典型成员 |
|---|---|---|---|
| **基底** | `SurfaceClass.BASE` | 占据全屏、无交互、不承载信息 | `WedoBackground` |
| **内容** | `SurfaceClass.CONTENT` | 承载业务信息，随数据变化，可在页面内滚动 | 课程块、列表行、设置分组卡、表单组、空状态 |
| **浮层** | `SurfaceClass.FLOAT` | 浮在内容之上，有独立 z 序，可被「收起/关闭」 | 底栏、顶栏、Sheet、Dialog、Picker、浮动按钮 |

**判定口诀**（写进卷 06 的 KDoc，也写进评审清单）：

> 它会随滚动一起走吗？会 → CONTENT。
> 它是常驻的还是可关闭的？常驻但浮在上面 → FLOAT（条带）。可关闭 → FLOAT（大面）。
> 它承载的是数据还是操作？数据 → CONTENT。操作 → FLOAT。

按这个口诀，`SettingsCards` 被划为 **CONTENT**（承载设置项数据，随页面滚动），而它上面的开关 `WedoToggle` 的 knob 被划为 **CONTENT 内的子元素**，不做独立材质——这条会在卷 05 的 L-10 展开。

### 2.2.2 采样规则（V2 从未定义的部分）

| 规则 | 内容 |
|---|---|
| **R-UP-1** | 只有 FLOAT 可以采样它下方的任何内容（BASE + CONTENT + 更低层 FLOAT 的合成结果） |
| **R-UP-2** | CONTENT **不得**采样任何东西。它的材质是 G0（镀层），不是采样 |
| **R-UP-3** | BASE **不得**采样，也不得被采样为「玻璃内容」——它只提供明度场 |
| **R-UP-4** | 同层级之间不采样。两个并列的 CONTENT 卡片互不影响 |
| **R-UP-5** | 嵌套深度 ≤ 2：页面级 Host → 浮层 Host。第三层禁止（ADR-18 的延伸） |

**R-UP-2 是本次改造最容易被违反的一条。** 给课程卡「加一点模糊会更好看」的冲动，会让 60+ 块同屏的滚动直接崩掉（`CourseTableView.kt:143` 的注释已经预警过）。

### 2.2.3 二级页底色去重（结构修复）

**问题**：18 处不透明底色。经逐行核实，官方原稿「12 个二级页各自 `Scaffold(containerColor)`」的说法**不准确**，真实情况是三种机制：

| 机制 | 处数 | 位置 |
|---|---|---|
| `Scaffold(` 用**默认** `containerColor` | 10 | `AddCourseScreen:451`、`AllTablesScreen:63`、`AppearanceScreen:93`、`EditTableScreen:149`、`ExportScreen:120`、`GeneralSettingsScreen:105`、`HolidaySettingsScreen:162`、`LicenseScreen:79`、`ReminderScreen:149`、`WidgetEditScreen:60` |
| `Scaffold(containerColor = colors.background)` | 1 | `EditTableScreen:97` |
| `Modifier.fillMaxSize().background(colors.background)` | 7 | `JwImportActivity:415`、`ExportScreen:121`、`GeneralSettingsScreen:106`、`HolidaySettingsScreen:163`、`ReminderScreen:150`、`TodayScreen:133`、`TodayScreen:318` |

**关键机制**：`Theme.kt:476` 有 `MaterialTheme(colorScheme = m3Scheme)`。所以 `Scaffold()` 的默认 `containerColor` 就是 `m3Scheme.background`，**同样不透明**。「没写 `containerColor`」不等于「没涂底色」——这一点是原稿最大的误判。

外加 2 处 `WedoBackground`：`MainActivity.kt:451`（主入口）与 `ImportWizard.kt:226`（导入向导自己又包一层 → 环境纹理会叠两份）。

**后果**：即使 `WedoBackground` 有了环境纹理，二级页一进来就被一层不透明底色盖住 → 页内任何浮层都采不到纹理。

**修复规则**：

| 规则 | 内容 |
|---|---|
| **R-BG-1** | **全部 11 处 `Scaffold`** 的 `containerColor` 改为 `Color.Transparent`（含 10 处用默认值的） |
| **R-BG-2** | 7 处 `.background(colors.background)` 全部删除；`TodayScreen` 的两处都删 |
| **R-BG-3** | 唯一的不透明底色由 `WedoBackground` 提供（`MainActivity.kt:452`） |
| **R-BG-4** | 页面内的「卡片底色」不受影响——那是 CONTENT 的 `surface`，不是 BASE |
| **R-BG-5** | `ImportWizard.kt:226` 的第二个 `WedoBackground` **保留**（导入向导可能在独立 Activity 中），但必须提供与 `L-01` 同一套环境层参数 |
| **R-BG-6** | `JwImportActivity` 是独立 Activity，不在 `MainActivity` 的 `WedoBackground` 内 → 它自己的底色**不能全删**，只做去重 |

**为什么这条在 P1 而不是 P2**：如果不先去重，P2 做出来的底栏玻璃采到的仍是纯色，会被误判为「参数不对」而反复调参——这是典型的「修错了地方」。

### 2.2.5 一条容易被忽略的规则：SurfaceClass 由容器决定，不由组件类型决定

`WedoIconButton` 出现在两个地方：

- 课表顶栏右侧的「添加」→ 所在容器是 `WedoWeekHeader`（FLOAT）→ 它继承 FLOAT 的材质上下文
- 设置页某行右侧的「更多」→ 所在容器是 `SettingsCards`（CONTENT）→ 它继承 CONTENT

**如果按组件类型判定**，`WedoIconButton` 会被统一归为某一类，然后两处都错。

| 规则 | 内容 |
|---|---|
| **R-CLS-1** | `SurfaceClass` 的判定的第一依据是**最近的已分类祖先**，不是组件自身 |
| **R-CLS-2** | 只有 `WedoBackground`、`WedoTabBar`、`WedoWeekHeader`、三类 Sheet、`WeekPicker`、`AlertDialog` 是「分类根」——它们自己声明 `SurfaceClass` |
| **R-CLS-3** | 其余组件通过 `LocalSurfaceClass` 读取最近根的分类，不自行声明 |

这条规则让「按容器判定」变成可机械执行的：新组件只要不声明 `SurfaceClass`，就自动继承。只有分类根需要显式声明。

R-CLS-3 也解释了为什么卷 06 的公开 API 面里有一个 `LocalSurfaceClass` CompositionLocal——它不是可选的便利设施，是分类体系的传递机制。

## 2.3 颜色与环境色彩响应

### 2.3.1 现有色板不动

11 个系统色（`WedoAppleTokens.kt:63-73`）、`legacyAliases` 的 Yellow→Orange（`:82-83`）、强调色三角色（`accent` / `accentIcon` / `accentText`，`:750/762/777`）**全部保留**。

理由：这是 A2 品牌锚点。玻璃改造是通过「材质」提升质感，不是通过「换色」提升质感。换色会同时触发 A1 与 A3 两个锚点的风险，且让对比度矩阵需要重算 22 组。

### 2.3.2 BASE 层环境纹理（D8 的落地）

**目标**：给玻璃提供可采的内容，同时不引入任何品牌色、不重犯 2026-09-27 的「彩色身份」否决。

**方案：两层静态叠加，无动画。**

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **V-01** | 径向明度场 | 中心 `(50%, 38%)`，半径 `shortestSide × 0.85`，中心 `L +1.2%`，边缘 `L −0.8%` | ΔL 全程 ≤ 2%，肉眼几乎不可辨，但模糊后能看出「不是纯平」 |
| **V-02** | 确定性噪点 | 种子 `0x57ED0`，幅度 ±1.5/255，1 图素/px，64×64 tile 平铺 | 主作用是**防色带**（banding），次作用是给模糊提供高频 |
| **V-03** | 深色模式明度场 | **不做提亮**，改为中心 `L +0.6%` 的极淡高光 | OLED 用户对纯黑被提亮极度敏感；深色下宁可几乎没有，也不要把黑变成深灰 |
| **V-04** | 深色模式噪点 | 幅度 ±1.2/255（略低于浅色） | 黑底上噪点更显眼，需压低 |

**三条硬约束**：

1. **必须静态**。不得用 `rememberInfiniteTransition` / 任何逐帧变化。项目当前这类 API 零使用，引入会带来常驻重绘。
2. **必须确定性**。同一设备同一分辨率下每次渲染结果一致，否则 golden 测试无法做差分。
3. **必须可关闭**。`GLASS_ENABLED = false` 时退化为今天的纯色（`#F2F2F7` / `#000000`），一字不差。

**实现要点（供卷 06 引用）**：

- 噪点用 64×64 的 `ImageBitmap` 生成一次，`BitmapShader(REPEAT)` 平铺。避免每帧算随机数。
- 明度场用 `Brush.radialGradient` 一次绘制。
- 两者都在 `WedoBackground` 的 `drawBehind` 里，**不改布局**（B-06）。

**成本**：一次性位图（64×64×4 = 16KB）+ 一次径向渐变绘制。零逐帧成本。这是整份计划里性价比最高的一项。

### 2.3.3 为什么不用品牌色做环境层

被否决过的方案是「背景用课程色的低饱和大面积模糊」（类似 Apple Music 封面取色）。理由不是不好看，是三条硬冲突：

| 冲突 | 说明 |
|---|---|
| 违反 V2-04 / A3 | 「颜色承载语义，不承载装饰」。背景色不表达任何信息 |
| 与 A1 打架 | 课程色是「哪门课」的编码。背景大面积染色会让课程块的色彩编码失效 |
| 触发历史否决 | 2026-09-27 的否决正是「彩色身份」路线 |

→ 列为 NG，永久不做。

## 2.4 透明度体系：4 档不动，另立一套

### 2.4.1 为什么不改现有的 4 档

`WedoTheme.Alpha` 有四档：`highContent .8` / `hairline .3` / `tinted .12` / `inactive .6`（`Theme.kt:325-337`），**65 处引用**。

直接把它扩成 8 档，会让 65 处引用全部需要重新判断「我原来用的是语义还是数值」。这是典型的「重构伪装成改进」。

**决策**：保留 `WedoTheme.Alpha` 作为**内容 alpha**（文字、图标、禁用态），另立 `GlassAlpha` 作为**材质 alpha**（tint、rim、hairline-on-glass）。两套并存，职责不同，命名区分。

| 套 | 管什么 | 引用数 | 是否改 |
|---|---|---|---|
| `WedoTheme.Alpha` | 内容的不透明度（文字淡化、禁用态、hairline 分割线） | 65 | **不改** |
| `GlassAlpha`（新） | 材质的不透明度（tint 底色、rim 加光、玻璃上的 hairline、内高光） | 0 → N | 新建 |

**为什么必须分开**：内容 alpha 是「让文字变淡」，材质 alpha 是「让玻璃变透」。两者的取值逻辑完全不同——文字的 0.8 是「次级文字」，材质的 0.8 是「几乎不透明的玻璃」。混在一套里，调材质时会误伤文字。

### 2.4.2 GlassAlpha 的取值

| ID | 参数 | 浅色 | 深色 | 说明 |
|---|---|---|---|---|
| **V-10** | tint alpha（G0 基底） | 0.62 | 0.48 | 沿用 `regular` 风格的既有值作为起点 |
| **V-11** | tint alpha（G1/G2 采样后叠色） | 0.18 | 0.22 | 已经有真实背景，tint 只需微调色相，不需要遮盖 |
| **V-12** | rim alpha | 0.60 | 0.38 | 沿用 `EDGE_LIGHT` / `EDGE_DARK`（`WedoGlassTokens.kt:91-92`） |
| **V-13** | hairline alpha（玻璃上） | 0.25 | 0.42 | 深色下暗线更必需——黑底没有暗线就没有边界 |
| **V-14** | 内高光 alpha | 0.60 | 0.60 | 沿用 `INNER_HIGHLIGHT`，深色不降——黑底更需要顶部受光 |
| **V-15** | 禁用态材质系数 | ×0.60（rim 保留 ×0.85） | 同 | 禁用不等于消失：rim 衰减慢于 tint |
| **V-16** | 按下态 tint 增量 | +0.06 | +0.05 | 按下时玻璃「变实」而不是「变亮」 |

**V-10 与 V-11 的落差是本次改造的一个关键判断**：G0 的 tint 必须够厚（0.62），因为它是**假装**有一层玻璃；G1/G2 有真实背景，tint 反而要薄（0.18），否则真采样被自己的染色盖住，等于白做。

### 2.4.3 alpha 与对比度的耦合

`B-02` 要求「玻璃面板内的文字按最差背景验算」。落地规则：

| 规则 | 内容 |
|---|---|
| **R-CONTRAST-1** | 玻璃面板上文字的最低对比度按 `TARGET_ACCENT_TEXT_CONTRAST = 4.5` 验算（`WedoAppleTokens.kt:301`） |
| **R-CONTRAST-2** | 验算背景取「面板背后最亮」与「最暗」两极，取劣者 |
| **R-CONTRAST-3** | tint alpha 与 rim alpha 不得同时降低；至少一个保持基线，否则文字失去依托 |
| **R-CONTRAST-4** | 课程块内的 6.5:1（`TARGET_TEXT_CONTRAST`，`:187`）**不受本卷影响**——CONTENT 恒 G0 且底色不透明（D7 / B-01） |

R-CONTRAST-4 是整份计划里最重要的一条保护。它保证了「玻璃改造不会连累课程块可读性」——这也是把课程块划为 G0 而非采样玻璃的核心原因。

## 2.5 透射层级

本卷只定义**层级语义**，数值（blur sigma / frost）归卷 04 的 O-ID。

### 2.5.1 三个透射等级

| 等级 | 标识 | 背后内容可见度 | 载体 |
|---|---|---|---|
| **T0** | 不透明 | 0% | CONTENT（课程块、卡片底色） |
| **T1** | 半透 | 约为 tint 的余量（V-10 中 0.62 → 38% 可见） | G0 材质 |
| **T2** | 采样 | 真实采样 + 模糊 | G1 / G2 |

### 2.5.2 层级可见性规则

| ID | 规则 | 理由 |
|---|---|---|
| **V-17** | 相邻透射等级之间的明度差 ≥ 3% | 低于 3% 人眼难辨，看起来像「没做」 |
| **V-18** | 最多 3 层叠透（BASE → CONTENT 间隙 → FLOAT） | 超过 3 层，最底层的内容已不可辨，只剩浑浊 |
| **V-19** | 同一视口内不得出现两个 T2 面板相邻 | 两块真采样并排，会形成「磨砂带」，视觉上像故障 |

V-19 的落地：底栏与顶栏若同时在视口内（顶栏滚离态 + 底栏），其一必须降为 T1。这条在卷 05 的 L-02/L-03 里体现为「顶栏与底栏不得同时 G2」。

## 2.6 边缘高光（Rim）与厚度感

### 2.6.1 厚度 = 四件事之和，缺一即塌

| 组成 | 作用 | 缺了会怎样 |
|---|---|---|
| Bevel 折射带 | 边缘内容被弯折 | 玻璃变成「贴纸」（L0 无此项，靠 V-24 补偿） |
| Rim（1dp） | 边缘受光的加光带 | 玻璃没有「边」，像一块雾 |
| Hairline（0.67dp） | 最外圈压暗 | 浅色底上玻璃与背景糊在一起 |
| 阴影 | 落地 | 玻璃「浮」不起来，像画上去的 |

这四项的顺序不可换：折射 → tint → rim → hairline → 阴影。顺序错了会出现「阴影盖住 rim」这类低级错误。

### 2.6.2 Rim

| ID | 参数 | 设计起点 | 说明 |
|---|---|---|---|
| **V-20** | rim 宽度 | 1.0dp（L0 用 1.2dp） | L0 无折射，需更宽的 rim 补偿厚度 |
| **V-21** | rim 方位调制 | 顶 0.62 / 斜 0.28 / 侧 0.10 | **自建值**，不沿用 FlClash 的 0.68/0.03（那是 iOS 27 拟合，与本项目色调不同） |
| **V-22** | hairline 宽度 | 0.67dp | 沿用 `kLine` 量级；再细会在 xxhdpi 上消失 |
| **V-23** | hairline 方位插值 | `\|normal.x\|³` | 侧边比上下更暗；三次方保证只有接近侧面才压暗 |
| **V-24** | L0 档 rim 双环 | 外环暗（`V-13` 的 0.7×）+ 内环亮（`V-12` 的 1.0×） | 无折射时，双环是唯一能造出「边缘有厚度」的手段 |
| **V-25** | 内高光覆盖范围 | 顶部 34% 高度，向下渐隐 | 沿用 `INNER_HIGHLIGHT_EXTENT` |

**V-21 为什么要自建**：FlClash 的 0.68/0.03 是在 `saturation 2.08–2.84` 的高饱和背景下拟合的。本项目的 CONTENT 是中性灰阶，同样的方位比会让侧面 rim 直接消失，玻璃看起来只有上边有光。0.62/0.28/0.10 保留了「顶部主导」但侧面仍可见。

### 2.6.3 Rim 与裁剪轮廓必须同源

这是**最容易翻车的一处**。项目当前的圆角是 `WedoAppleShapes.continuous()`，即 `RoundedCornerShape` 半径 `×1.2` 的 squircle 近似（`Theme.kt:644`）。它与真超椭圆在长边入角处最大差约 1.8% 半径。

| 规则 | 内容 |
|---|---|
| **V-26** | rim 的绘制路径与面板 `clip` 必须使用**同一个** `Shape` 实例 |
| **V-27** | 不得一处用 `RoundedCornerShape(16.dp)`、另一处用 `continuous(16.dp)`——虽然看起来只差 3.2dp，但 rim 只宽 1dp，错位 0.5dp 就露馅 |

**为什么不做真超椭圆**（与 V2-16 的 `REVISE` 呼应）：Compose 1.7.4 无原生 squircle 支持，自绘 `Path` 会破坏 `clip()` 的硬件加速路径，收益（1.8% 半径差）远小于成本与风险。改为「近似保留 + 强制同源」，把问题从「几何精度」转为「一致性」，这是可执行的。

→ 登记为 U-13，若未来 Compose 提供原生 squircle 再评估。

### 2.6.4 小尺寸面板的 rim 退化（32dp 以下禁止材质）

rim 宽 1dp，这是**绝对宽度**，不是相对宽度。这带来一个几何后果：

| 面板高度 | rim 占单边比例 | 观感 |
|---|---|---|
| 52dp（底栏） | 1.9% | 正常，边缘有光 |
| 44dp（触控最小） | 2.3% | 正常 |
| 32dp（Chip / 按钮） | 3.1% | 边缘光开始抢戏，看着像描边框 |
| 24dp（Toggle） | 4.2% | 已经是「框」不是「边」 |

**规则**：

| ID | 规则 | 说明 |
|---|---|---|
| **V-28** | 高度 < 32dp 的元素**不得使用材质**（G0 也不行） | rim 占比 ≥ 3.1%，视觉上退化为描边矩形 |
| **V-29** | 高度 32–44dp 的元素若必须用材质，rim 宽度降为 0.75dp | 保证占比 ≤ 2.3%；44dp 以上自然回到 V-20 的 1dp |

**这条规则解释了一个看起来矛盾的决定**：`WedoChip` 与 `WedoToggle` 被划为「无材质」（§2.2.4），不是因为它们不重要，是因为它们的尺寸撑不起 rim。

Chip 高度由 `WedoChipHeight` 常量控制（`ScheduleHeaderLayoutContractTest:149-156` 锁住了 `.height(WedoChipHeight)` 的写法），若其值 < 32dp，则 V-28 自动生效，无需额外判断。

### 2.6.5 Rim 与 Border 不是一回事

这两个词在日常表述里常被混用，但在实现上是两件不同的事：

| | Rim | 描边（Border / Stroke） |
|---|---|---|
| 位置 | 面板**内部**最外 1dp | 面板边界上，可内可外 |
| 颜色 | 白（加光），alpha 随方位变化（V-21） | 任意色，alpha 恒定 |
| 混合模式 | `screen` 或 `plus`（加色） | `srcOver`（覆盖） |
| 作用 | 模拟边缘受光，制造厚度 | 划分区域 |
| 消失条件 | 深色底上可减弱，但不消失 | 可完全去掉 |

**三条不可互换的理由**：

1. **加色 vs 覆盖**：描边会盖住背后的像素；rim 是加光，背后仍然可见。用描边替代 rim，玻璃边缘会变成一条实线，失去「光」的质感。
2. **方位调制**：rim 的 alpha 随法线方向变化（顶部 0.62 → 侧面 0.10）。描边的 alpha 是常量，无法表达「光从上方来」。
3. **与裁剪的关系**：rim 必须与 `clip` 同源（V-26）；描边通常画在边界上，不参与裁剪计算。

**反例**：用 `Modifier.border(1.dp, White.copy(alpha = 0.6f), shape)` 冒充 rim。这在纯白背景上看起来「差不多」，在深色或复杂背景上会立刻暴露——因为它是一条均匀的白线，没有受光方向。

V2-02 的原文「层级靠留白与字重，不靠边框与阴影」在这里第一次需要被精确化：**它禁止的是「用边框划分区域」**，不禁止「用加光模拟受光」。这是 `REVISE` 而非 `SUPERSEDE` 的原因。

## 2.7 阴影与景深

### 2.7.1 现状：全库 1 处

`.shadow(` 在全仓只出现 1 次（`SettingsCards.kt:93`）。这意味着当前界面完全没有空间层级——所有元素「贴在纸上」。

玻璃如果没有阴影，就只是一块带光边的半透明矩形。**阴影不是装饰，是玻璃「浮起来」的唯一依据。**

### 2.7.2 双层阴影

| ID | 参数 | 浅色 | 深色 | 说明 |
|---|---|---|---|---|
| **V-30** | 近层 | blur 3dp / offsetY 1dp / alpha 0.10 | alpha 0.24 | 制造「贴着内容」的接触阴影 |
| **V-31** | 远层 | blur 24dp / offsetY 8dp / alpha 0.08 | alpha 0.20 | 制造「离地高度」 |
| **V-32** | 深色模式放大 | — | 近层 ×2.4 / 远层 ×2.5 | 深色下阴影需要更强才可见（黑对黑的对比天然弱） |
| **V-33** | 景深映射 | 底栏 8dp / 顶栏 6dp / Sheet 12dp / Dialog 16dp | 同 | offsetY 直接表达「离地高度」 |
| **V-34** | 阴影不进捕获 | 阴影绘制在玻璃合成**之后** | 同 | 阴影若被采进玻璃，会形成「阴影里有阴影」的重影 |

**V-33 的语义**：底栏离地 8dp（常驻、贴着内容）、Dialog 离地 16dp（模态、阻断）。用户不需要被告知，但视觉上会自然读到「谁更靠上」。

### 2.7.3 阴影的约束

| 约束 | 说明 |
|---|---|
| 阴影不得用于 CONTENT | 内容层靠留白与底色建立层级（V2-02 的保留部分）；给 60+ 课程块加阴影 = 60 次离屏 |
| 阴影不得用于「选中态」 | 选中靠 accent，不靠抬高 |
| 阴影强度不参与动画 | 阴影随面板出现/消失淡变，但不得逐帧改变 blur 半径（会触发重绘） |

## 2.8 课程色与背景明度的耦合（A1 锚点的保护）

### 2.8.1 耦合在哪里

课程块底色 = 11 色之一 × 55% 淡底（叠在 `surface` 之上），文字色由 `solveForContrast` 反解（`WedoAppleTokens.kt:171/204-237`），门槛 6.5。

这套推导的**隐含前提**是：底色叠在**固定的 `surface`**（浅色 `#FFFFFF` / 深色 `#1C1C1E`）之上。

### 2.8.2 玻璃改造会不会破坏它

**不会，但只有一条防线**：`B-01` —— CONTENT 层底色不透明度不得降低。

如果哪天有人觉得「课程块半透明一点更好看」，55% 会变成 55% × 背景透射率，底色随背后的东西变化 → `solveForContrast` 的解不再成立 → 某些课程在某些位置会掉到 4:1。

| 规则 | 内容 |
|---|---|
| **V-35** | 课程块底色 alpha 恒为 1.0（淡底是「颜色混合后的实色」，不是「带 alpha 的颜色」） |
| **V-36** | 混合计算在**取色阶段**完成（颜色 → 55% 混 `surface` → 得到不透明色），不在绘制阶段用 alpha |
| **V-37** | G0 镀层（rim / 内高光 / 阴影）叠在不透明底色之上，不改变底色 |

V-36 是可执行的关键：现在 `WedoCourseCard` 若用 `color.copy(alpha = 0.55f)` 绘制，就必须改成 `blend(color, surface, 0.55f)` 得到一个不透明色。这个改动看起来只是写法差异，但它决定了玻璃改造会不会连累 A1。

### 2.8.3 U-05：色种不一致

`WedoCourseCard.kt:41` 用 `courseName` 取色，`CourseColorUtil.kt:169/224/231/262` 用 `groupId`。同一门课在 App 内与桌面小组件可能不同色。

玻璃化会让这个问题**更明显**：G0 镀层提高了颜色块的视觉权重，色差更容易被注意到。

→ 列为 U-05，倾向纳入本次范围（统一到 `groupId`，因为 id 比名字稳定：改名不该换色）。

### 2.8.4 G0 镀层在课程块上的绘制层序

课程块是 CONTENT + G0，它同时有「课程色底」和「G0 镀层」。这两者的层序如果搞反，颜色会整体偏亮或偏暗，且 6.5:1 会静默失效。

**唯一允许的层序（自下而上）**：

```
① 课程色底（不透明，V-35/V-36 已混合完成）
② 内高光（顶部 34%，V-25，alpha V-14）
③ Rim（边缘 1dp，方位调制 V-21，alpha V-12）
④ Hairline（最外圈 0.67dp，方位插值 V-23，alpha V-13）
⑤ 内容（文字 / 图标 / 时间）
⑥ （无阴影——CONTENT 不投影，见 §2.7.3）
```

| ID | 规则 | 理由 |
|---|---|---|
| **V-38** | 内高光必须画在课程色底**之上**、内容**之下** | 若画在内容之上，文字会被「蒙一层白」，对比度下降 |
| **V-39** | Rim 与 Hairline 必须画在**内容之下** | 若画在内容之上，边缘文字会被加光/压暗，字形边缘失真 |
| **V-40** | **同屏数量 > 12** 的重复内容单元**不得**有阴影 | 60+ 块同屏，阴影 = 60 次 `blur` 离屏。适用对象是「高密度重复单元」：课程块（60+）不可，设置分组卡（≤ 6）可，今日页条目（≤ 12）可 |
| **V-41** | G0 镀层的 alpha 不参与按压动画的 `translation` 通道 | 按压只改 `scale`，不改镀层 alpha（否则每帧重绘 Paint） |

> **PATCH-04（2026-10-26，第 4 轮）**：写卷 05 的 `L-18` 时逐行核实发现，原稿「12 个二级页各自 `Scaffold(containerColor = colors.background)`」是**错的**：真正铺不透明底色的有 **18 处**，其中 10 处用的是 `Scaffold` 的**默认** `containerColor`（因为 `Theme.kt:476` 设置了 `MaterialTheme(colorScheme = m3Scheme)`，默认值就是主题背景色，一样不透明）。
> 处置：`R-BG-1` 从「二级页 `Scaffold`」扩为「全部 11 处 `Scaffold`（含用默认值的）」；`R-BG-2` 明确 7 处 `.background()` 全删；新增 `R-BG-5`（`ImportWizard` 的第二层保留）与 `R-BG-6`（`JwImportActivity` 是独立 Activity，底色不能全删）；`V-40` 的阈值由「> 10」改为「> 12」（今日页 ≤ 12 条应可用近层阴影）。
> 原因分类：**事实错误**（不是表述不清，是数错了）。这是本轮最有价值的一条更正——如果按原稿实施，改完 11 个 `Scaffold` 还会漏掉 7 处 `.background()`，然后「为什么二级页的玻璃还是采到纯色」会被归因为「参数不对」。

> **PATCH-03（2026-10-26，第 3 轮）**：`V-40` 初版写「课程块不得有阴影」，措辞让人以为「CONTENT 全部不许投影」。写卷 05 的 L-10（设置分组卡）时发现该卡同屏 ≤ 6 个、应当有近层阴影，与 L-11（课程块，60+ 个）的正确处置不同。
> 处置：把 `V-40` 的适用对象明确为「同屏数量 > 10 的高密度重复单元」，并显式给出反例边界（分组卡可用）。原因分类：**条款表述不精确**，非设计变更。

**V-38 / V-39 是「文字在材质之上」这条通用规则的第一次具体化**。它的推广形式是：**任何材质的 rim 与 hairline 都不得覆盖文字层**。底栏、顶栏、Sheet 同理。

这条规则有个副作用需要提前说明：如果面板高度很小（如 44dp 的条带），内容会与 rim 非常接近，此时 V-52 的「最小内缩 8dp」会成为布局约束——但 B-06 规定材质不改 padding。这两条如何共存？

答案是：**padding 由布局决定，不因材质而改；若 padding 已经小于 8dp，则该面板不应用材质**（回到 V-28 的尺寸门槛逻辑）。这样「不改 padding」与「不压字」都不破。

## 2.9 字体、图标、内容与材质的协调

### 2.9.1 字体不动（F-01）

无内置字体，走系统默认。`WedoTypography` 15 档、`WedoAppleType` 11 档均不设 `fontFamily`。本轮不改，理由：

1. 内置 PingFang 有授权问题（U-09）。
2. 系统默认字体在中文环境下已是苹方/思源，视觉上不缺。
3. 换字体是全局风险，与材质改造正交。

### 2.9.2 玻璃面上的文字

| ID | 规则 | 理由 |
|---|---|---|
| **V-50** | 主文字色用 `onSurface`，**不用** `onSurfaceVariant` | `onSurfaceVariant` 在玻璃上会与 rim 叠加后发灰 |
| **V-51** | 次级文字 alpha ≥ 0.72 | 低于 0.72 时，rim 的加光会吃掉字形边缘 |
| **V-52** | 文字与 rim 的最小内缩 8dp | rim 宽 1dp + 视觉呼吸；低于 8dp 文字会「贴边」 |
| **V-53** | 玻璃面板的 padding ≥ 12dp | 同上，且要容纳内高光（V-25 覆盖顶部 34%） |

**V-50 是一条硬规则，不是偏好。** 现有代码里 `onSurfaceVariant` 使用频繁，玻璃化后必须逐处审查——这也是卷 05 每个 L-ID 的「现存问题」里必须列出的项。

### 2.9.3 玻璃面上的图标

| ID | 规则 | 理由 |
|---|---|---|
| **V-54** | 玻璃面上的图标**禁用** `accentIcon`，改用 `onSurface` | B-12 的延伸：rim 的加光会与 accentIcon 争夺注意力，且对比度无法保证 |
| **V-55** | 选中态图标仍用 `accentIcon`，但**只在 rim 之外**（即面板边缘内侧 ≥ 6dp） | 选中态是语义，必须保留；但不能被 rim 吃掉 |
| **V-56** | 图标尺寸不随材质变化 | 材质不改规格，这是 ADR-21 的延伸 |

**V-54 与 A2 的冲突如何处理**：A2 说强调色三角色分离是品牌锚点。V-54 说玻璃面上不能用 accentIcon。

两者不矛盾：A2 保护的是「三角色存在的必要性」，V-54 约束的是「在哪不能用」。玻璃面上的图标本来就不是「强调」对象——它们是导航或操作，用 `onSurface` 更符合层级。

真正需要 accentIcon 的场合（底栏选中项、设置页选中行），其位置都在面板边缘内侧，V-55 已经覆盖。

## 2.10 浅色、深色与复杂背景

### 2.10.1 三套取值

| ID | 场景 | 浅色 | 深色（`#1C1C1E` 系） | 深色（纯黑 OLED） |
|---|---|---|---|---|
| **V-60** | rim alpha | 0.60 | 0.38 | **0.44** |
| **V-61** | hairline alpha | 0.25 | 0.42 | 0.48 |
| **V-62** | tint alpha | 0.62 | 0.48 | **0.52** |
| **V-63** | 阴影放大 | ×1.0 | ×2.4 | ×2.8 |

**纯黑为什么要单独一档**：OLED 纯黑下，rim 的加光会被绝对黑「吃掉」——因为加光是在近黑底上相加，感知提升被压缩。同时阴影在纯黑上完全不可见（黑对黑），只能靠 rim 与 hairline 建立边界。所以纯黑档的 rim 与 hairline 都要**加强**，而阴影放大只是形式上的（实际不可见）。

### 2.10.2 复杂背景规则

「复杂背景」指：玻璃面板下方是内容而非空 BASE。典型场景是底栏浮在课表网格上。

| ID | 规则 | 说明 |
|---|---|---|
| **V-64** | 背景方差 > 0.18 时，tint alpha + 0.08 | 防止背后是高对比内容时文字被干扰 |
| **V-65** | 方差 > 0.32 时，额外叠一层 `Veil`（匀色） | 极端情况（半黑半白）下，仅靠 tint 不够 |
| **V-66** | 方差计算在捕获时做，不在每帧 | 每帧算方差 = 每帧遍历像素，成本不可接受 |

V-66 是关键：方差必须在 `Bake` / `LiveStrip` 的捕获阶段顺带算（图集已经在手上），不能单独做一次全图扫描。

### 2.10.3 系统无障碍设置

| ID | 设置 | 响应 |
|---|---|---|
| **V-67** | 系统「增大对比度」开启 | 强制 G0 + rim ×1.25 + hairline ×1.4（`HIGH_TEXT_CONTRAST_ENABLED`） |
| **V-68** | 系统「移除动画」开启 | 材质不降级（材质不是动画），但所有过渡改为跳变。见卷 03 §3.7 |
| **V-69** | 字号缩放 ≥ 1.3× | 玻璃面板高度按内容撑开，不得裁切；rim 宽度不变 |

V-67 对应 V2-30 的 `REVISE`：原条款要求「支持增大对比度」，但从未落地。本次接上。

### 2.10.4 主题切换期间的视觉一致性

当前主题切换是**同帧硬切**（`Theme.kt:396-480`），无过渡。玻璃化会放大这个问题：硬切时，材质参数（V-10..V-16、V-60..V-63）会整组跳变，观感上像「换了一个 App」。

**这不是必须解决的问题**，但必须明确它的边界，否则实施者会顺手加一个 `animateColorAsState` 然后引入新的不一致。

| ID | 规则 | 说明 |
|---|---|---|
| **V-45** | 主题切换**默认不加过渡**，保持现有硬切 | 加过渡需要改 `WedoBackground` + 全量 colors 读取路径，收益中等、风险高（U-06 相关） |
| **V-46** | 若未来加过渡，**材质参数不得逐帧插值** | `rim alpha` 逐帧插值会让 rim 在过渡中「闪」——因为加光在中间值上最不自然 |
| **V-47** | 若未来加过渡，只允许 `< 200ms` 的 `alpha` 交叉淡化，且材质参数在切换瞬间**已完成**取值 | 材质不需要「渐变」，需要「瞬时切换 + 整体淡化掩护」 |

**为什么材质参数不能插值**：rim 是加光运算，在 alpha 0.60 与 0.38 之间的中间值（如 0.49）上，加光量会落在一个「半亮不亮」的区间，观感上比两端都差。这与普通颜色插值不同——颜色插值有明确的中点，加光没有。

V-45 与 V-47 合起来的意思是：**主题切换保持现状，不在本计划范围内做过渡**。这条写进卷 01 的 NG 需要补充说明——它不是「不值得」，是「单独一个议题」。

### 2.10.5 滚动期间的视觉稳定性（判定部分）

玻璃面板在滚动中会出现一类特有缺陷：**磨砂内容随滚动「跳像素」**。表现为背景纹理在面板内一格一格地移动，而不是连续滑动。

根因在捕获的亚像素对齐（数值归卷 04 的 O-ID），但**判定标准属于本卷**，因为它是纯视觉现象。

| ID | 判定标准 | 观察方法 |
|---|---|---|
| **V-42** | 滚动时，玻璃面板内的背景内容不得出现「整格跳变」 | 录屏 3 秒，逐帧比对面板内某条固定纹理的位置 |
| **V-43** | 滚动停止后，面板内内容必须在 2 帧内稳定 | 同上，停止时刻起算 |
| **V-44** | 静止时，面板内内容不得有任何闪烁 | 静止录屏 10 秒，逐帧比对 |

**V-42 的量化口径**：把录屏导入逐帧工具，取面板内一条高对比纹理（如课程块的边界线），记录其每帧 y 坐标。若相邻两帧的位移为 1.5dp 与 0.0dp 交替出现（而不是 0.75/0.75 均匀），即为「跳像素」。

这条缺陷在 60Hz 上不容易看出来（每帧位移大），在 120Hz 上非常明显——而项目默认钉最高刷率（`util/HighRefreshRate.kt:20-44`，`AppPrefs.kt:251` 默认开）。**所以 V-42 必须按 120Hz 判定，不能按 60Hz。**

### 2.11.3 三层 Token 的职责边界

```
第 1 层  原始数值   WedoGlassTokens（常量）+ 本卷 V-ID
第 2 层  解析结果   GlassSpec（data class，一次计算，多次使用）
第 3 层  绘制指令   drawBehind 里的实际 Brush / Path / Paint
```

| 规则 | 内容 |
|---|---|
| **V-70** | 第 1 层的数值只允许出现在 `WedoGlassTokens.kt` 与本文档中。其他文件出现字面量即缺陷（SC-08） |
| **V-71** | 第 2 层必须由纯函数 `buildGlassSpec(...)` 产出，可 JVM 单测，不依赖 Compose 环境 |
| **V-72** | 第 3 层不得做任何条件分支判断（`if (dark) ...`）——所有分支在第 2 层完成 |

V-72 是性能要求：绘制阶段的分支会在每帧执行，而解析阶段的分支每个面板只执行一次。
